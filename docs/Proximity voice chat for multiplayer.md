# Put proximity voice on a self-hosted SFU

Build proximity voice as a service beside the game, not inside it: a self-hosted **LiveKit** SFU on the k3s box, with every client joining with automatic subscription off and the game hosts deciding, from positions they already own, which speakers each listener receives. This is the only option in the notes that is open source, complete to operate, deployable on one k3s node today, gives a client one media session that does not care which host simulates the player, and gives echo cancellation and jitter handling on both native and browser without the team writing them. The alternative, Opus frames as datagrams on the game's own QUIC/WebTransport connections, is feasible in 2026 and needs no new deployment or login step, but it puts audio fan-out on the game hosts, ties voice to a multi-host layer that has not yet passed its go/no-go, and leaves the jitter buffer and native echo cancellation to the team. The recommendation is conditional on a short spike, because four facts that decide it are unverified: the native cost of linking libwebrtc, whether a LiveKit token can stop a client subscribing itself, how fast server-driven subscription changes take effect, and whether LiveKit's host-network deployment works on this box. If the spike fails on the native dependency or on subscription control, fall back to the datagram design. In both designs the hard part is the same and belongs to the game: a low-rate, cross-region, cross-host "who is near whom" computation that does not exist today. Fortress mode has no documented proximity precedent; the notes point to a non-positional fortress channel, which is a decision for the game's owner.

A note on confidence. Claims with a link or a file path were read by the researchers. Sentences tagged *(inference)* are reasoning on top of those findings, by the researchers or by this report. Sentences tagged *(unverified)* are things nobody confirmed. Nothing was built, run or measured.

## The game starts with no audio, no datagrams and no UDP service in the cluster

Three facts about the repository shape every option. First, **the client has no audio at all**: no audio crate in `Cargo.lock`, Bevy built with `default-features = false` and without `bevy_audio` (`Cargo.toml:118-140`), no microphone or Web Audio features in the `web-sys` list (`crates/client/Cargo.toml:108-120`). Voice is the project's first capture, codec, mixing and playback code on both targets.

Second, **nothing sends a QUIC or WebTransport datagram today**. Every packet is its own reliable unidirectional stream on native quinn and in the browser (`crates/server/src/webtransport.rs:1-4`, `crates/client/src/netcode_web.rs:1-7`). The pinned libraries support datagrams (quinn-proto 0.11.13 enables them by default; wtransport 0.7.1 exposes `send_datagram` / `receive_datagram`), so a datagram path is an addition at four edges, not a library change. All server output also funnels through one shared writer task with two recorded incidents of a stalled client wedging it for everyone (`crates/server/src/lib.rs:455-490`).

Third, **the game server is not in Kubernetes**. The orion k3s box runs only HTTP services behind Traefik with cert-manager and Route53 (login, Keycloak, site, Zulip, Garage, monitoring); the public game server is a Docker Compose container on the same machine with UDP 6466/6467 published directly, running `local` auth (`deploy/web/compose.yml`). No UDP service is exposed through k3s, and the host firewall lives in another repository (`~/Projects/mod/mods/survival-world`). The multi-host layer (R3) is "BUILT 2026-11-13, go/no-go PENDING … nothing has been run live or measured" (`TODO.md:157`).

Position data is the last constraint. Poses live inside region threads (`crates/game/src/state.rs:367-390`); the manager knows only which region holds each player (`world_manager/mod.rs:923-926`). Clients subscribe to whole regions, and at the play default (region edge 256 m, near radius 0) a client holds its own region plus the fortress neighbourhood (`crates/client/src/world_scale.rs:18-29`). The only cross-region mirror is an 8-block halo (`crates/game/src/halo.rs`). So no single place, on server or client, knows who is within earshot across a region edge *(inference)*.

## Two real architectures, and why the others fall away

Every documented implementation that scales past a small lobby has a server decide audibility and forward only audible speech; client-side-only filtering and peer-to-peer meshes are documented only for small sessions ([Simple Voice Chat server source](https://github.com/henkelmax/simple-voice-chat/blob/26.3/common/src/main/java/de/maxhenkel/voicechat/voice/server/Server.java), [LiveKit: receiving tracks](https://docs.livekit.io/home/client/receive/)). Two shapes fit this game.

| | A. Self-hosted LiveKit SFU, server-driven subscriptions | B. Opus datagrams over the game's QUIC/WebTransport |
|---|---|---|
| Server | Apache-2.0 SFU, v1.13.11, official Helm chart, single UDP port mode ([releases](https://github.com/livekit/livekit/releases), [ports](https://docs.livekit.io/home/self-hosting/ports-firewall/)) | Relay code inside each game host; nothing new to deploy *(inference)* |
| Who hears whom | `autoSubscribe: false` plus server API `UpdateSubscriptions` ([docs](https://docs.livekit.io/home/client/tracks/subscribe/)) | Host forwards a speaker's datagrams only to listeners in range *(inference)* |
| Across hosts | One media session per client, independent of hosts *(inference)* | Frames ride observer connections or peer links; a body hand-off moves the uplink mid-sentence *(inference)* |
| Native client | `livekit` crate 0.11.0 with capture, playout, AEC/NS/AGC via libwebrtc ([changelog](https://docs.rs/crate/livekit/latest/source/CHANGELOG.md)) | cpal + Opus + own jitter buffer; no echo cancellation at first |
| Browser client | `livekit-client` JS on the page; the Rust SDK has no wasm target ([README](https://github.com/livekit/rust-sdks)) | `getUserMedia` + WebCodecs Opus + WebTransport datagrams ([MDN](https://developer.mozilla.org/docs/Web/API/WebTransport/datagrams), [caniuse](https://caniuse.com/mdn-api_audioencoder)) |
| Auth | New room token minted by the game backend | None: the session is already authenticated |
| Main risk | Integration and operations: C++ dependency, two SDKs, SDK churn, a UDP service in k3s | Audio quality engineering, plus load on the game hosts |

### What LiveKit buys

LiveKit is actively released (roughly two to four server releases a month in 2026; the latest page shows day and month only, the year is inferred) and its README lists selective subscription, moderation APIs, speaker detection and JWT authentication ([README](https://raw.githubusercontent.com/livekit/livekit/master/README.md)). Nothing needed for proximity voice is Cloud-only; Cloud adds a global mesh, enhanced noise cancellation and observability ([Cloud docs](https://docs.livekit.io/intro/cloud/)). Its one published audio benchmark forwarded 10 publishers to **3,000 subscribers at 80% of 16 cores** ([benchmark](https://docs.livekit.io/home/self-hosting/benchmark/)). From that single data point the researchers estimate a few hundred concurrently listening players per core for proximity groups of about five talkers *(inference; no proximity benchmark exists, and none for many-publisher rooms)*.

The decisive property is structural. Voice services in the documented products are separate from the simulation process and keyed by a channel, which is exactly what makes a server boundary irrelevant to them ([Vivox](https://docs.unity.com/en-us/vivox-unity/developer-guide/channels/large-3d-channel-settings), [LiveKit](https://docs.livekit.io/home/client/receive/)). The counter-example, Simple Voice Chat, keeps voice in the game server process and its range query sees only players of that server ([source](https://github.com/henkelmax/simple-voice-chat/blob/26.3/common/src/main/java/de/maxhenkel/voicechat/voice/server/ServerPlayerManager.java)). No published account of voice across a seamless-world boundary was found for any game, so this argument is inference from product documentation, not from a shipped example.

### What the datagram path buys, and what it costs

The steelman for B is strong. WebTransport datagrams became Baseline in March 2026 when Safari 26.4 shipped them ([webrtc.ventures](https://webrtc.ventures/2026/04/webtransport-is-now-baseline-what-it-means-for-real-time-media/)); WebCodecs Opus encoding is in Chrome 94+, Firefox desktop 130+ and Safari 26+ but not Firefox for Android ([caniuse](https://caniuse.com/mdn-api_audioencoder)); quinn drops the oldest unsent datagrams when its buffer fills, which is the right behaviour for voice ([quinn docs](https://docs.rs/quinn/latest/quinn/struct.Connection.html)). The connection is already encrypted and authenticated, the server already owns positions, and no roster of participants ever reaches a client. A 20 ms Opus frame is far below the 1,200-byte safe datagram size *(inference)*. Simple Voice Chat shows a small team can ship this tier to a large player base ([Modrinth](https://modrinth.com/plugin/simple-voice-chat)).

The costs are specific to this codebase. Audio fan-out must bypass `WorldManager`, the region threads and the shared writer, or it adds load exactly where the wedge incidents happened *(inference)*. Cross-host voice depends on R3 peer links, which are stream-based and unaccepted. QUIC datagrams share one congestion window with the reliable streams ([RFC 9221](https://rfc-editor.org/rfc/rfc9221)), and whether quinn schedules datagrams ahead of bulk stream data during terrain streaming was not confirmed. No Rust crate provides an adaptive jitter buffer; str0m excludes one explicitly ([README](https://github.com/algesten/str0m)). Native echo cancellation would rest on pure-Rust ports at version 0.1.0 ([sonora](https://docs.rs/crate/sonora/0.1.0)). Safari does not support the older `datagrams.writable` send path ([MDN PR](https://webproxy.poorya-velaei-d67.workers.dev/https://github.com/mdn/content/pull/44317)). Finally, B does not meet the stated hosting goal by itself: voice would live wherever the game hosts live, and they are not in Kubernetes yet.

## Hosts decide who hears whom; the SFU only obeys

The audibility decision is game logic and stays in the game. The proposed shape, all of it inference from the notes:

Each region thread emits a low-rate, non-simulation side output of its players' voice positions, two to four times a second. Vivox recommends 2 to 4 position updates per second and Odin at most 10 ([Vivox](https://docs.unity.com/en-us/vivox-unity/developer-guide/channels/positional-channel-configuration), [Odin](https://www.4players.io/odin/ai-training/unreal/reference/)). This data is never a `GameEvent`: audio state is outside rollback and hashing and must stay there. The manager converts poses to world coordinates and computes each listener's audible set from its own regions and the eight neighbours; with a 256 m region edge and a voice range of tens of metres, nothing further away matters. Where a neighbour region belongs to another host, the positions near the shared edge travel over the peer link as a `Volatile` message, which already means "never replayed". The existing 8-block halo is too narrow for a 30 m range, so this is a new flow.

**One authority per listener**: the host that holds the listener's body sets that listener's subscriptions, so two hosts never fight over one participant during a hand-off. The host calls LiveKit's `UpdateSubscriptions` with the result. A body hand-off (`HomeHop`) changes which host computes, and the media session does not reconnect.

Room layout follows from one rule in the notes: **never one room per host**, because that recreates the seam. Start with one room per world. A LiveKit room must fit on one node ([benchmark](https://docs.livekit.io/home/self-hosting/benchmark/)); when a world outgrows that, move to a grid of rooms decoupled from host territories, the model Dissonance documents ([tutorial](https://placeholder-software.co.uk/dissonance/docs/Tutorials/Proximity-Chat.html)).

### Radius, edges and what the listener needs

Published audible radii cluster between 25 and 50 m: VRChat 25 m, Vivox 32 m with full volume inside 1 m and inverse rolloff, Simple Voice Chat 48 blocks with a 24-block whisper ([Vivox properties](https://docs.unity.com/ugs/en-us/manual/vivox-unity/manual/Unity/developer-guide/channels/positional-channel-properties), [SVC config](https://modrepo.de/minecraft/voicechat/wiki/server_config)). No source publishes hysteresis margins, fade times or a cap on simultaneous speakers. The workable rule is to subscribe a little beyond the audible radius, unsubscribe further out still, and let the client's curve reach zero at the audible radius so the transport edge is never heard *(inference)*. Dissonance documents the hard cut-off that results otherwise ([tutorial](https://placeholder-software.co.uk/dissonance/docs/Tutorials/Proximity-Chat.html)). A nearest-N cap bounds bandwidth in a crowd *(inference; Vivox's warning about many participants at one point is the only published sign that density is a load problem)*.

The listener's client needs each audible speaker's position to pan and attenuate. Speakers in a subscribed region are already in the client's predicted state; a speaker 20 m away across a region edge often is not. The home host therefore sends a small packet naming the audible speakers and, for those outside the client's subscribed regions, their positions *(inference)*. The same packet should be the only place a client learns who a participant is: range enter and leave events act as a radar that reveals a silent, unseen player, a real concern underground in a voxel world *(inference)*. Use opaque participant identities in LiveKit and map them to players only while audio is delivered *(inference; what a LiveKit participant list reveals to a restricted client was not checked)*.

### Adventure body versus commander camera

Every client has a body in both modes; in Fortress it stands inert while the camera flies (`docs/superpowers/specs/2026-11-14-creative-mode-and-chat-design.md`). Adventure maps cleanly: mouth and ears are the body, with camera yaw for panning *(inference)*.

Fortress has no shipped precedent. No RTS or colony sim was found that documents proximity voice for body-less players; the one design document found uses team voice ([Iron Curtain](https://iron-curtain-engine.github.io/iron-curtain-design-docs/decisions/09g/D059/D059-overview-text-chat-voip-core.html)). The server does not know where a commander is looking (the focus point is client-only), and a free camera used as a listening point would be an eavesdropping device over anyone with a body *(inference)*. The nearest precedent is Simple Voice Chat's spectator rule: body-less participants neither speak to nor hear proximity by default ([config](https://modrepo.de/minecraft/voicechat/wiki/server_config)). The recommended default is therefore a **non-positional fortress channel** for the players of one fortress, with commanders outside proximity *(inference)*. In the SFU this needs no second room: a listener's subscription set is the union of the proximity set and the fortress set, and the client plays the fortress set without spatialisation *(inference)*. Whether an adventurer standing in the fortress hears the commanders, the "open" versus "isolated" group flag in Simple Voice Chat, is an owner decision. Whether co-owners share a server-side identity to key the channel on (`fortress: Option<SiteId>` in `PlayerRecord`) was not traced.

### Multiplayer only, announced by the server

Nothing in `ServerPacket` tells a client the auth mode, the single-player flag or the player count. The robust rule is server-driven: a host that offers voice sends an availability packet carrying the SFU address and a token; a single-player server (`VOXEL_SINGLE_PLAYER=1`) never sends it *(inference)*. Restricting voice to `jwt` sessions also excludes `local`-auth servers, where anyone may claim any name (`crates/server/src/auth_edge.rs:6-9`); that covers the current public deploy. All voice state on the client is per-world and must be registered with the session lifecycle or it leaks into the next world.

## One host-network pod on k3s, two client integrations

### Deployment

LiveKit's Kubernetes model is host networking with one pod per node, and it does not support private clusters behind extra NAT ([Kubernetes docs](https://docs.livekit.io/home/self-hosting/kubernetes/)). On a single node with a public address that is simple: set `rtc.udp_port` 7882 so all media uses **one UDP port**, keep ICE/TCP 7881 as the fallback, set `rtc.use_external_ip`, and put the WebSocket signalling (port 7880) behind the existing Traefik Ingress with a cert-manager certificate, which must be CA-signed ([ports](https://docs.livekit.io/home/self-hosting/ports-firewall/), [deployment](https://docs.livekit.io/home/self-hosting/deployment/)). That is two firewall openings, made in the other repository, and no Redis until a second node exists *(inference)*. Skip TURN/TLS at first: on one IP it collides with the Ingress on 443, and a browser that cannot send UDP cannot play the game over WebTransport anyway *(inference)*.

The repository shape is a new root `deploy/envs/orion/<name>/` plus `deploy/modules/<name>/`, with the API key and secret as `random_password` and a Kubernetes secret, a `ServiceMonitor` for LiveKit's Prometheus endpoint (`:6789/metrics` when `prometheus_port` is set), a justfile recipe and a line in CLAUDE.md's root order *(inference from the login module's pattern)*. Lower the chart's five-hour termination grace period, which is sized for meetings; on one node an upgrade drops voice, because the new pod cannot bind the host ports until the old one exits *(inference)*. The Helm chart's values were not read and the docs name only GKE, EKS and DOKS, so k3s with Traefik is unverified. Whether k3s here has ServiceLB enabled is unknown and irrelevant under host networking. Growth is more nodes, one LiveKit pod each, plus Redis, with each node reachable by clients; STUNner is worth its relay hop only where nodes have no public address ([webrtc.ventures](https://webrtc.ventures/2026/08/stunner-production-kubernetes/)). Box capacity is not documented, and voice shares the machine with the game server, Postgres, Keycloak and monitoring.

### Tokens

The hosts verify JWTs today but hold no signing key; the login service signs Ed25519 join tickets with audience `mmo-host` and a 300 s lifetime, unsuitable as a voice credential (`crates/login-api/src/lib.rs:8-42`). Since the hosts need the LiveKit API secret anyway to drive subscriptions, the host mints the room token after `Hello` succeeds and delivers it in the availability packet *(inference)*. The alternative, minting in the login service at `/v1/join`, keeps secrets off hosts but still leaves hosts needing API access. LiveKit tokens being HS256 JWTs signed with the API secret, and the grant fields that restrict subscribing, are *(unverified)* in the notes.

### Native client

Pin `livekit` exactly (it went from 0.7 to 0.11 within 2026). Since 0.7.40 its `PlatformAudio` layer captures the microphone with echo cancellation, noise suppression and gain control through libwebrtc, and received audio is available as per-participant PCM through `NativeAudioStream` ([changelog](https://docs.rs/crate/livekit/latest/source/CHANGELOG.md), [README](https://github.com/livekit/rust-sdks)). The room runs on the tokio networking edge and hands PCM to a small mixer over channels *(inference)*. Because no game audio exists, the mixer is new either way: per-speaker gain from distance and constant-power stereo pan, about thirty lines, on a dedicated cpal output stream *(inference)*. `bevy_seedling` 0.8 is the likelier future Bevy audio engine and has optional HRTF, but its web backend needs cross-origin isolation, which this project has ruled out ([firewheel-web-audio](https://lib.rs/crates/firewheel-web-audio)).

Three native unknowns remain. Binary size and build time of the prebuilt libwebrtc are *(unverified)*: background knowledge says hundreds of MB to download and tens of MB in the binary. The signalling TLS can be built with rustls and ring per the `livekit-net` manifest ([Cargo.toml](https://raw.githubusercontent.com/livekit/rust-sdks/main/livekit-net/Cargo.toml)), but transitive defaults could still pull `aws-lc-rs`; check with `cargo tree -i aws-lc-rs`. And whether libwebrtc's echo canceller works when the game, not the SDK, plays the far-end audio is *(unverified)*. Until that is known, native ships push-to-talk by default.

### Browser client

The page already owns the WebTransport sessions and is the only place `getUserMedia` and Web Audio can run, so voice never crosses the worker boundary *(inference)*. Load `livekit-client` on the page and drive it from wasm through thin JS glue; the browser's own WebRTC stack does capture, echo cancellation, Opus and jitter buffering. Each remote track feeds a `GainNode` and `PannerNode`. LiveKit's own tutorial lists the pitfalls: attach each remote stream to a hidden muted `<audio>` element or the graph stays silent, start a new source far away until its first position arrives, and smooth position changes ([tutorial](https://livekit.com/blog/tutorial-using-webrtc-react-webaudio-to-create-spatial-audio/)). The page's existing `AudioContext` resume hook covers the autoplay rule (`crates/client/index.html:315-365`). The shared abstraction between targets stays thin: join, publish or mute, and "set speaker S's position and gain" *(inference)*.

### Interface

Push-to-talk is a client-only key read by its own Bevy system behind the `TextEntry` typing gate, never through `map_key`, so it cannot become a sim input. V, T, G, B, M, E and Q are taken. The speaking indicator belongs in `hud.slint`; device, volume and mute settings would be the game's first settings screen. No player names travel in the game protocol today and no nameplates exist, so labelling speakers and a persistent mute list both need a name source added first.

## Security, moderation and legal flags

The safe pattern in the notes has three parts: the game connection authenticates the player and hands out a per-session voice credential, a server decides who receives audio, and clients never connect to each other. An SFU satisfies the third, since media is relayed and peers do not see each other's addresses *(inference)*. The second holds only if the token forbids self-subscription; otherwise the server filter is advisory and a modified client can listen anywhere. That grant is the single most important thing to verify.

Mute and block must be enforced at the server, not as a local volume of zero. Vivox applies block lists server-side and wants them at login, because blocking on the participant-added event lets initial audio through ([Vivox](https://docs.unity.com/en-us/vivox-unity/developer-guide/channels/large-3d-channel-settings)); here the block list is simply an input to the audible-set computation *(inference)*. A `LoginToHost::Kick` must also end the voice session, by a short token lifetime or an explicit remove-participant call *(inference)*. No moderation, mute, block or report data model exists in the repository.

The legal points are flags, not advice, and several rest on search digests because Ofcom's page refused the fetch. A game with voice between strangers and UK users is likely in scope of the UK Online Safety Act, with a compulsory illegal-content risk assessment ([Ofcom](https://www.ofcom.org.uk/online-safety/the-online-safety-act-and-gaming-know-the-risks-know-the-rules-know-how-to-comply), [Lewis Silkin](https://www.lewissilkin.com/insights/2025/10/24/ofcom-issues-guidance-about-online-safety-act-in-video-gaming-context-102lr5v)). In the EU, the DSA's notice-and-action duties apply at any size ([Article 19](https://www.springlex.eu/en/packages/dsa/dsa-regulation/article-19/)); whether live, unstored voice counts as hosting is unanswered. Recording for moderation brings consent and data-protection duties ([Unity Safe Voice](https://docs.unity.com/ugs/en-us/manual/safe-voice/manual/privacy/privacy-overview)); voice that is never stored cannot be reviewed after a report. Fortnite ships proximity chat off by default and Roblox has required an age check before any chat since January 2026 ([Fortnite](https://www.fortnite.com/news/introducing-proximity-chat-incorporate-new-social-interactions-in-your-fortnite-islands), [Roblox](https://www.businesswire.com/news/home/20260107986568/en/Roblox-Requires-Users-Worldwide-to-Age-Check-to-Access-Chat)). COPPA, GDPR age-of-consent rules and the biometric status of relayed voice were not researched.

## A spike first, then the smallest useful slice

The spike exists to kill the recommendation cheaply. It has five checks, each with a pass condition. One: add the `livekit` crate to a throwaway binary and measure clean build time, binary size and `cargo tree -i aws-lc-rs`; with workspace feature unification on, do this outside the main dependency graph. Two: mint a restricted token and confirm a client cannot subscribe itself, and record what the participant list shows it. Three: time `UpdateSubscriptions` from call to first audio and find out whether each change renegotiates; the docs say subscribing needs a negotiation handshake ([docs](https://docs.livekit.io/home/client/tracks/subscribe/)). Four: run LiveKit host-networked on k3s with the UDP mux port and connect from outside, native and browser. Five: on native, capture through `PlatformAudio` while playing through the game's own mixer and listen for echo; in the browser, run the JS SDK beside the Bevy WebGL2 main loop and listen for glitches. If check one or two fails, switch to design B and start it on the existing connections, measuring datagram queue age during terrain streaming.

After the spike the order is: the deployment root; the availability packet and token, `jwt` sessions only; voice positions out of region threads and the audible set on one host; the browser client with push-to-talk, since it is the cheaper of the two; the native client; the fortress channel; names, mute, block and report; then cross-host audibility over peer links, once R3 has passed its own go/no-go. Open microphone, occlusion and HRTF are later polish. Occlusion done on the listener's client is cosmetic; done on the server it is also a privacy property but costs a path query per pair *(inference)*. The notes give no sourced effort figures for this path; their only estimate, two to four engineer-weeks for a push-to-talk tier, is a researcher's judgement about design B.

## Conclusion

The research changes the question. "SFU or datagrams" turns out to be the smaller decision: both need the same new piece of game logic, a cross-region and cross-host audibility set at a few hertz, and both need the client's first audio code on two platforms that share almost nothing below the mixer interface. What the SFU changes is where the risk sits. It moves risk out of audio engineering and out of the unaccepted multi-host layer, into a dependency and a deployment that a week of measurement can accept or reject. That asymmetry, cheap to test versus open-ended to tune, is the reason to try it first.

The decisions that belong to the owner are few and none are technical. Is voice wanted at all, given the design documents never mention it? What does a commander hear and say: a fortress channel, nothing, or a point in the world? Does an adventurer in a fortress hear its commanders? What is the audible radius, and is there a whisper? Push-to-talk or open microphone by default, and is voice opt-in? Do `local`-auth servers ever get voice? Is voice recorded around reports or never stored, what is the minimum age, and are UK players admitted before a risk assessment exists? Is a large C++ dependency in the native client acceptable if the spike shows its cost? Which native platforms matter? And under which hostname does the service live: the repository uses `factoriosurvivalworld.com` throughout, while the owner's notes name a different domain for the game.
