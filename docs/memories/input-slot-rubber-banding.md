ROOT CAUSE (live-measured 2026-09-20 with new `[client-mispredict]` / `[client-motion]` probe lines): one ordered event stream per region; the client predicts its input right after its own tick k, the server assigned the slot by ARRIVAL. They only agree if two free-running tick clocks match to a fraction of a tick, and nothing made them (client tick thread = `send(Tick); sleep(rate)`, controller bang-banged 45/55 ms around drift 0). Result: EVERY input mispredicted (mispredicts/input >= 1.0 in every window); home-region kinds were `tick>input` (client ahead) and `input>tick` (behind). Each correction moved the player up to **3.454 u = exactly one tick of walking** (a key edge landing a tick early/late), avg 0.5–2.75 u, and the rendered camera visibly stepped backwards. This supersedes the "join ~13 events behind" framing in [[client-prediction-runaway]] as the steady-state cause.

FIX (committed 8e90481, only my hunks staged): `ClientPacket::GameEventAfterTick(event, after_tick)` — client stamps home's `current_tick()` at prediction; `WorldManager` forwards `RegionInput::EventAfterTick` only when `event.region_id == homes[cid]` (tick counters are per region); `RegionRunner` holds it until its tick counter reaches the stamp (arrival order, released right after `tick()`, `MAX_INPUT_LEAD_TICKS` = 1 s bound, flushed on Shutdown); late/unstamped = apply on arrival = old behaviour (so the lockstep harness, where the client trails by a tick, is unchanged). Client pacing now targets `CLIENT_LEAD_MS` = 1.5 ticks with a ±1 tick band instead of flapping around 0. Tick-number slotting chosen over predicted-id slotting because relayed ghost updates shift ids every tick near region borders. Tests: 6 new in `crates/game/tests/region_runner.rs` incl. end-to-end "leading client reconciles a stamped input with 0 rollbacks, unstamped rolls back".

LIVE RESULT 1 (capture 20260920T175827Z): in-region mispredicts 4–40/s → 0–1.8/s and every home correction 0.000u — slotting works. But roaming ran the lead away (drift 150→950 ms at the slowest rate, evlog 15→158, corrections to 62u; user: "went a bit crazy, jittering and moving forward" while walking/jumping — spawn is 128u from two region borders). Cause: ONE client tick clock, but each region's offset to its server twin is fixed when its snapshot loads (fresh = behind), and EVERY region's SyncClock steered the global rate → fresh regions keep demanding speed-up → older regions' lead inflates (pre-existing; earlier captures already showed drift +500). FIX 2 (uncommitted): clock follows HOME's SyncClock only; any other region is stepped into the lead band by `align_region` (extra predicted ticks now, or `stalled` ticks skipped via `World::progress_world_one_tick_except`); home is stepped too when > band + `HOME_STEP_ALIGN_MS` (3 ticks) out; `MAX_ALIGN_TICKS` 2 s; `[client]` line now shows home drift + `aligned=n(ticks,home=n)`. LIVE RESULT 2 (capture 20260920T180319Z, user: "seems improved"): home drift pinned +50..100 ms at tick_rate=50 (no flapping), evlog 1–5, mispredicts 0–6/s (was up to 70), game thread util 5–9%, replayed/5s 0–118 (was ~900), `aligned=` fires in bursts right after new regions load with home=0–1. Remaining home corrections are ONLY `tick>transfer` at region crossings (n=2–4 per crossing, avg 1.5–8.7u, max 17.5u) = the handoff/EntityArrived ordering item below. The 9 `dropping PlayerInput: home … not loaded` WARNs are all in the first 0.5 s before the home snapshot loads — harmless.

STILL OPEN, measured same capture: (1) `transfer>tick` ≈ 1 mispredict PER TICK per neighbour region (home=0, replay depth 12–16) whenever ghost mirrors are relayed — client ticks all regions in lockstep, server regions tick on independent phases, so the relayed GhostUpdate never lands at the predicted id; invisible to the player, pure waste; same tick-slot idea would fix it. (2) Camera `lerp(0.3)` PER FRAME → trailing distance ∝ frame time (3–5 u avg, 5–35% larger on chunk-crossing frames, crossing frames spike 41–66 ms vs ~29) — make it time-based or do two-pose tick interpolation. (3) `[client-motion]` "sim pose stepped back ~1000u" is a probe artefact at region flips (picks another camera entity), ignore. Client harness tests (`reconcile_keepup`, `crossing`, `harness_smoke`) NOT run after this change — slow, ask first.
