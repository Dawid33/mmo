# R4 — Takeover: a host fails over alone, on-demand claiming, drain Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Status (2026-11-15): BUILT — all 19 tasks done on `develop` (`b4f58b31` … `85187467`); the whole-branch review, its one fix wave and the scoped re-review are done. Dawid's hand checks, the client test runs and a live `go-nogo-r3` are still open (`TODO.md`). See "Amendments made during execution" at the end.** Originally a DRAFT: Written 2026-11-13 at `b328e1d5`; re-checked 2026-11-14 at `12e4d4a0` (64 commits later: Keycloak sign-in, the login service on orion, the voxel terrain return, the seam slot order) — see "Re-checked on 2026-11-14" below.

**Goal:** When one region host of a multi-host world dies or hangs, another host takes its super-regions from the last committed world cut and the world keeps running: no other host restarts, every entity, player and person exists exactly once, and the players of the dead host reconnect by themselves. A leaving host's land is taken by another host when someone needs it, a world cut survives a peer-link drop, and ownership is a claim in Postgres instead of a fixed hash.

**Architecture:** Ownership becomes a trait over a **directory** (`super_regions.owner`, mirrored in memory on every host) with three policies: `AllInOne`, `Static` (R3 as built, kept unchanged) and the new `PgClaim`. Each host renews a **lease** on its `hosts` row from its main loop; the coordinator — the fenced singleton that already sequences cuts — declares a lapsed host dead in ONE transaction that also gives all its super-regions to one **heir** (a *succession*). Because a session forgets a message once it is acknowledged, every host now keeps a **peer journal** of the state messages it exchanged with each peer since the last committed cut; the survivors send theirs to the heir, which resolves each entity id by its latest event (drop the stale copy from the dead host's stored regions, or deliver the copy the dead host had received), and the next committed cut settles the succession. The world generation stays as the last resort (`Static`, a total crash, a second failure before a succession is settled, the operator).

**Tech Stack:** Rust (dated nightly); sqlx 0.8 runtime queries, Postgres 17 (`PREPARE TRANSACTION`, row locks, `now()` as the one lease clock) and SQLite column-for-column; quinn 0.11 + rustls (ring) via `svc-link`; crossbeam between threads, tokio only at network edges; Bevy 0.19.1 client, Slint UI.

**Spec:** `docs/superpowers/specs/2026-09-20-multi-instance-k8s-postgres-research.md` §0.4 (b) (ownership behind a trait, fencing always in Postgres), §0.5 R4, §7 (lease rows, one heartbeat per instance), §0.10; handoff `docs/superpowers/plans/2026-11-13-r4-takeover-handoff.md`; predecessor `docs/superpowers/plans/2026-11-12-r3-multi-host.md` (decisions 1–13, "Amendments made during execution", the Task 14 crash table) and its ruling `.superpowers/sdd/2026-11-12-r3-multi-host/task-13-ruling.md` (cut ownership on the wire). Command form: `just test-one <crate> "--test <target> -- <filter> <filter>"` — cargo needs the `--` before name filters and before flags such as `--include-ignored`.

## Verified against the code on 2026-11-13 (`b328e1d5`) — read before starting

Where the handoff's premises differ from the code:

- **The peer queues do NOT say what is owed after a crash.** `PeerSession` pops an entry when it is acknowledged (`game/src/peer/session.rs`, the ack arm of `pump`); `cut_peer_rows` / `cut_peer_players` (`world_manager/peers.rs`) see only unacknowledged entries. A survivor therefore has no record of what crossed to or from the dead host since the last cut. Restoring the dead host's regions from cut K beside survivors that ran on gives: an entity that crossed dead → survivor after K twice (live, and in the dead host's K rows); one that crossed survivor → dead after K and was acknowledged nowhere. This is exactly why R3 rolls the whole world back (decision 7). R4 needs the peer journal (Task 7); `departed` only helps for players.
- **No single-host failover can conserve items exactly.** A player picks up a pile on host D after K and walks to host S; D dies; D's regions come back at K with the pile, the player keeps the items. Undoing it on S taints everything that player touched since. Only a whole-world restart from K, or logging every state change of D synchronously, is exact. See decision 1 — it is Dawid's to confirm.
- **Claims are made once per boot and never released**; `HostClaims.fence` is an immutable `Arc<Fence>` (`server/src/claims.rs`). `commit_check_set` is the touched super-regions ∪ every super-region in the fence (`world-store/src/fence.rs`): a host fenced anywhere commits nothing. That rule is kept: a live host is never taken over in part.
- **Ownership is a pure function in every process** (`Ownership::owner_of` → `rendezvous_owner`), read by ~40 call sites in `world_manager/{mod,peers,placement,world_cut,world_link}.rs`; the `super_regions.owner` column is read only by fence checks, `owner_claim_epoch` and the stale-row guard. Everything a host owes another is addressed to an **ordinal** (`peers`, `peer_waiting`, `departed`, `peer_endpoints`, `observer_tickets`, `foreign_running`), never to a region.
- **There is no heartbeat, lease or liveness anywhere.** The only signal is the QUIC link (`LINK_KEEP_ALIVE` 5 s, `LINK_IDLE_TIMEOUT` 15 s). A dead host does not roll the world back at once: its dirty `hosts` row blocks every cut (`CutsBlocked`), and the rollback happens when it boots again (`register_host`, the only writer of `world.generation`).
- **The coordinator admits a host by `MAX(epoch) WHERE owner = ordinal`** (`coordinator_rt.rs` `Routes::admit`, `owner_claim_epoch`); its own comment says a partial takeover or a layout change breaks it. Claims that change during a host's life break it for good — Task 5 replaces it.
- **`hosts.clean = 1` is written only by a committed two-phase leave** (`two_phase.rs`). A role-`host` process with `VOXEL_HOSTS=1` bumps the generation at every boot (harmless, one host).
- **Stored regions hold neither players nor people** (`PortableRegion.entities`: "neither a player nor a person"; players go to the `players` table, people are respawned by the coordinator at `RegionStarted`). The journal's drop set therefore only ever filters plain entities; a journalled person bundle is never delivered (Task 9).
- **`in_flight` rows carry `target_rx` / `target_rz`** and are scoped by `host` (`seq = host << 32 | i`); only `Fence::in_flight_scope()` adopts them. An heir adopts a dead host's rows through a new, explicit scope (Task 6).
- **Region incarnations come from one counter per manager process** starting at 0 (`next_incarnation`), so an heir's first incarnation of a region is below the dead owner's and the coordinator would drop its bounces (`DirectiveBounced` with `incarnation < latest`). Task 4 makes them world-ordered.
- **The seeded rig cannot kill one host** (`multi_rig.rs`: boots are fixed, `rebuild_from_last_cut` restarts every host). The real-process harness can (`server/tests/hosts.rs` `kill_host` / `restart_host`). Task 8 adds the rig half.
- **The client has no failover.** Losing the home ends the session (`instance.rs` → `GameError::Disconnected` → the world list). A lost observer connection is retried once through the home; a home that cannot reach the owner drops the subscribe silently (`peers.rs` `subscribe_elsewhere`) and nothing asks again. `RegionElsewhere` naming the home is ignored (`connections.rs`). The native client sets no QUIC keep-alive, so it notices a dead host after ~30 s (the browser after ~10 s). Login reaches the world through the entry host only; while that host is down every join is a 503.

## Decisions settled in planning

Each gives the trade-off first. Those that are Dawid's to overrule are repeated under "To confirm with the user".

1. **What a takeover conserves: identities exactly, items except across the dead host's seams.** Three options. (a) Keep R3's world rollback for every crash: exact, but every player of every host loses up to one save interval and reconnects, and the world stops until the dead host is back. (b) Log each host's state changes synchronously (a write-ahead log in Postgres or on the peers): exact and local, but a database round trip on the simulation path — a different engine. (c) **Chosen: per-host succession from the last cut.** Guaranteed: every entity, player and person exists exactly once (by id), in one place, and nothing is half-applied. Lost: what happened in the dead host's regions since the last cut (at most one save interval, that host only). **Not guaranteed:** item counts and terrain edits whose history crossed a seam of the dead host inside that window — an item picked up on the dead host and carried out exists twice, a block placed into the dead host from outside is gone with its item. The window is bounded (one save interval, the dead host's seams) and counted (`succession_seam_events=` on the `[server]` line: journal entries resolved). `VOXEL_OWNERSHIP=static` keeps (a) for anyone who wants exactness over availability.
2. **Ownership is a directory behind a trait, with one heir per predecessor.** `super_regions.owner` is the truth; each host mirrors it (`game::Directory`) and answers `owner_of` with `Me | Host(n) | Free | Unknown` — "wait, never guess": an `Unknown` or `Free` region is treated like one whose owner is unreachable today (a player is clamped at the seam, an intent is refused back, a transfer waits), never assumed. A dead or departed host's super-regions go to ONE heir, all of them, in one transaction: the peers' queues, the journal and the in-flight rows are per ordinal, so one heir makes "what was owed to host D" well defined; an heir per super-region would need every one of those re-keyed by region. Cost: the heir carries the dead host's whole load until a later rebalancing plan (R6) moves land again.
3. **Who triggers a takeover: a lease in Postgres, declared by the coordinator.** Peers' reports cannot tell a dead host from a cut link; the coordinator's own link cannot see a hung main loop. So each host writes `hosts.seen_ms` from its MAIN loop every `HOST_HEARTBEAT_MS` (a hung loop stops heartbeating although its sockets live) with Postgres' clock (§7: one clock, no skew). The coordinator declares a host dead when it has itself read the same `seen_ms` over `HOST_LEASE_MS` of successful reads (a database outage therefore never looks like every host dying) and the declaring transaction re-checks the lapse with `now()`. A host of the same ordinal that boots and finds its predecessor's dirty row vouches for the death (`seen_ms = 0`), which skips the observation time. Without the coordinator nothing is declared — the same dependency cuts already have.
4. **What stops two takers:** the declaration is one transaction under the coordinator fence and the `world` row lock (`FOR NO KEY UPDATE`, as `register_host` and `decide_cut`): it marks the row dead, inserts the succession row, and moves every super-region of the dead ordinal to the heir with `epoch + 1`. That UPDATE is the claim — the heir only reads its new fence. The dead process is fenced at its next write and its heartbeat matches no row (exit 3). No host pauses on a missed heartbeat: writes are fenced by epoch, and the survivors close their link to the dead boot before the heir starts anything, so a zombie can neither save nor exchange state.
5. **What an heir starts from.** The store at the last committed cut K (staged parts are resolved first; a succession is declared only between cuts), plus every survivor's journal against the dead host relative to K: per entity or player id the event with the highest stamp wins. Latest "a survivor received it from D" → the survivor's copy lives on; the id is dropped from D's stored regions and adopted rows. Latest "a survivor sent it to D" → D held it; the journalled bundle is delivered to the heir (a player is parked from it), and any copy in D's K rows is dropped. Nothing is written until the next cut: the heir filters in memory, loads every affected region and keeps it running, and that cut's commit decision settles the succession in the same transaction. A crash before it is settled leaves the store at K — which is what makes the generation a sound last resort.
6. **Intents are not journalled.** An intent the dead host had applied is one of its lost state changes; replaying it would need idempotent replies on every sender. Intents and replies still unacknowledged in a survivor's queue for the dead host were applied nowhere that survived: they are re-routed to the heir as they are. (Unacknowledged transfers and player moves need no special path — the journal holds them as `Sent`.)
7. **Drain = the leave cut, then a succession on demand.** A leaving host parks everything and its part is committed (as today); its row is clean and its claims stay. When a live host needs one of its regions the coordinator gives ALL its land to one heir by the same succession path with an empty journal (the leave pair's hold-back guarantees nothing crossed after the cut) — at once if the ordinal is beyond the configured host count, after `HEIR_WAIT_MS` otherwise (a rolling restart gets its land back; `just dev-r3` starts hosts a second apart). If it returns first it re-claims what the directory still says is its own. Nothing is decided by the leaver: where its regions go is the coordinator's rendezvous over the live hosts.
8. **The world generation survives as the last resort**, in four cases: `Static` ownership (R3 as built); a host that boots dirty when no other host is alive (a total crash: everyone restarts from the store anyway, and R3's rule already makes the later booters resume without a second bump); a second host declared dead before an open succession is settled (the journals needed to keep going are gone — every host restarts from K, with the land already at the heir); `worldctl rollback` by the operator.
9. **A cut survives a peer-link drop by marks through the coordinator.** Today a participant's link down aborts the cut because its `CutMark` cannot arrive. A mark is only a position in a numbered stream, so the count can travel another way: each side of a down link freezes its session until `CutDone` and reports `received_through` to the coordinator, which relays it; the sender then writes everything above the count as its own rows (the absent-peer rule), the receiver accounts for the rest. No cut while the coordinator is down stays as it is.
10. **Clients.** A client whose home died rejoins by itself: it asks the login service for a new join with its kept refresh token (no Keycloak round trip, no browser) and reconnects, for up to `REJOIN_MAX_MS`, on the screen the first join shows; it returns to the world list only when that fails, and to the sign-in screen only if the login service says the token is revoked. Its body is where the last cut (or the journal) left it. A client that only observed the dead host keeps its session: the home remembers the regions it could not serve and answers them when the directory names a reachable owner. Login still reaches the world through the entry host only; while the entry host is down nobody can join (several entry hosts are R5).
11. **`Static` stays exactly as built** (boot-time claims, held sessions for a leaver, world rollback). R3's tests keep running on it unchanged, and it is the escape hatch of decision 1. `just dev-r3`, `just host` and `go-nogo-r3` switch to `claim`; with every host alive and a fresh world the claim preference is the same rendezvous hash, so the layout — and the probe's `pick_seam` — do not move.

## Review Focus

- An older-generation `Attach` is told the generation instead of having its link closed.

## Extension points left for later plans (not planned here)

- **R5 (k8s):** StatefulSet; `max_prepared_transactions` in the CNPG cluster; clock sync across nodes (the lease already uses Postgres' clock; the world clock anchor does not); an advertised peer address (`peer_addr` is the bound one); certificate pinning for native QUIC from `HostEndpoint.cert_hash`; several entry hosts — until then a dead entry host stops logins.
- **R6 (autoscaling / rebalancing):** moving a super-region between two LIVE hosts (a planned hand-over: the giver parks and cuts, the taker claims) — the succession path with a live predecessor; it is what spreads an heir's load again and what a changed `VOXEL_HOSTS` needs.
- **Exact item conservation across a takeover** would need per-host write-ahead logging (decision 1 (b)).
- **Deferred as decided:** rate limiting, Postgres backups.
