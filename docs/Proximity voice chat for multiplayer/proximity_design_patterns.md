# Proximity voice chat: design patterns, tuning and pitfalls (state: November 2026)

Reading notes for the report writer:

- "Read from source" means I read the file in the project's repository (Simple Voice Chat, branch `26.3`, fetched 2026-11-14). "Search summary" means the claim comes from a search-result digest of the linked page, not from a full read of it — treat it as a lead with a lower confidence.
- Several of the named games (Rust, DayZ, PUBG, Sea of Thieves, Star Citizen, EVE, Valheim, LEGO Fortnite) publish no technical documentation of their voice layer that I could find. They are listed under Gaps, not filled in from memory.

## 1. Architecture patterns for deciding who hears whom

### Takeaway
Every documented implementation that scales past a small lobby has a server decide audibility and forward (or mix) only audible speech: the game server itself relays (Simple Voice Chat), or a voice service culls by positions it is given (Odin, Vivox positional channels), or an SFU is driven through a subscription API (LiveKit). Client-side-only filtering and peer-to-peer meshes are documented only for small sessions.

### Cited Findings

**(a) Relay through the game server**
- Simple Voice Chat runs its own UDP socket in the Minecraft server process (default port 24454/UDP) and relays every microphone packet itself. — [GitHub README](https://github.com/henkelmax/simple-voice-chat), [server config wiki](https://modrepo.de/minecraft/voicechat/wiki/server_config)
- The audibility decision is made on the server per microphone packet: `processProximityPacket` picks the distance (whisper distance or the default distance, then an add-on hook can change it) and broadcasts only to `getPlayersInRange(sender.level(), sender.position(), getBroadcastRange(distance), …)`. Read from source. — [Server.java](https://github.com/henkelmax/simple-voice-chat/blob/26.3/common/src/main/java/de/maxhenkel/voicechat/voice/server/Server.java)
- The range query is a plain linear scan over the players of the sender's level with a distance test, run for every packet; there is no spatial index. Read from source. — [ServerPlayerManager.java](https://github.com/henkelmax/simple-voice-chat/blob/26.3/common/src/main/java/de/maxhenkel/voicechat/voice/server/ServerPlayerManager.java)
- Plasmo Voice also uses UDP for voice; its port setting defaults to 0, meaning the same port number as the Minecraft server, and its guide recommends a dedicated port (search summary). — [Plasmo Voice setup guide](https://docs.emeraldhost.de/en/gameserver/minecraft-java-edition/plugins/setup-plasmo-voice), [Plasmo Voice repository](https://github.com/plasmoapp/plasmo-voice/)
- Dissonance (Unity) by default has a server component that manages the session and passes voice along to clients; text is always relayed through the server, and peers can optionally handshake to talk directly (search summary). — [Dissonance network protocol](https://dissonance.readthedocs.io/en/latest/Reference/Networking/Network-Protocol.html)

**(b) SFU / voice service with server-side selection by position**
- Odin (4Players): the client periodically sends its position to the Odin server, and the server then delivers voice only to nearby users, which reduces bandwidth and CPU (search summary). — [Odin Unreal C++ guide](https://docs.4players.io/voice/unreal/guides/unreal-cpp-guide/)
- Odin's `odin_room_update_position` sets the local peer's 3D coordinates in a room so that in large rooms peers only "see" each other when close; coordinates are in the engine's own units and the sensitivity is set with `odin_room_set_position_scale` (search summary). — [Odin core API](https://docs.4players.io/voice/core/api/functions/odin_room_update_position)
- Odin's Unreal reference says the position call is optional, exists only for performance and bandwidth (it is not needed for spatial audio itself), needs the room position scale set first, and should not be called more than 10 times per second; another Odin guide page suggests an update every couple of seconds (search summary; the two rates are a documented inconsistency, not necessarily a contradiction). — [Odin Unreal reference](https://www.4players.io/odin/ai-training/unreal/reference/)
- Odin Voice 2.0: each room supports up to 64 channels, each channel with its own 3D position and scaling (search summary). — [Odin Voice 2.0 blog](https://www.4players.io/blog/introducing-odin-voice-2.0)
- LiveKit: a participant can connect with `autoSubscribe: false`, after which "only explicitly subscribed tracks are delivered to the participant"; the docs name spatial applications as a use for this. — [LiveKit: receiving tracks](https://docs.livekit.io/home/client/receive/)
- LiveKit: the same control exists on the server API — `updateSubscriptions(room, identity, trackSids, subscribe)` subscribes or unsubscribes a given receiving participant, with equivalents in Go, Python, Ruby, Kotlin and Rust SDKs. — [LiveKit: receiving tracks](https://docs.livekit.io/home/client/receive/)
- LiveKit's spatial-computing page says that "on the client side" a space can scale to thousands of participants by choosing dynamically which streams each one receives (search summary). — [LiveKit use cases: spatial computing](https://livekit.io/use-cases/metaverse)
- Dissonance maps a continuous world onto rooms with an infinite grid: each cell is its own chat room and a player is placed into every cell within range of their position. — [Dissonance proximity chat tutorial](https://placeholder-software.co.uk/dissonance/docs/Tutorials/Proximity-Chat.html)
- Photon Voice: a forum answer says distance filtering has to be built with Interest Groups, subscribing and unsubscribing on the fly by distance (search summary; a forum reply, not documentation). — [Photon forum](https://forum.photonengine.com/discussion/comment/46267/)

**(c) Client-side filtering only**
- LiveKit's own spatial audio tutorial is this pattern: the backend only issues tokens, every spatial track gets a WebAudio renderer on the client, and the article describes no distance-based subscription at all. — [LiveKit spatial audio tutorial](https://livekit.com/blog/tutorial-using-webrtc-react-webaudio-to-create-spatial-audio/)
- Mumble positional audio: position data is produced on the client by a game plugin or the Link plugin and the server transmits positional data only to clients with a matching context; users with a different context are heard normally, i.e. non-positionally (search summary). — [Mumble positional audio documentation](https://www.mumble.info/documentation/user/positional-audio)
- A Valheim Mumble mod has an open issue titled "Can hear everyone no matter their distance" — the failure mode of a design where attenuation is purely a client setting (search summary; title only). — [valheimpositionalaudio issue 3](https://gitlab.com/jrobsonchase/valheimpositionalaudio/-/issues/3)

**(d) Positional channels in a voice service / server-side mixing**
- Vivox positional (3D) channels: "Vivox audio processing mixes all of the audio for every player, including volume attenuation over a distance and channel fading"; participant added/removed events fire as players enter or leave the maximum range. The page does not say where the mixing runs. — [Vivox positional channels](https://docs.unity.com/ugs/en-us/manual/vivox-unity/manual/Unity/developer-guide/channels/positional-channels)
- Vivox capacity: channels have a maximum of 200 participants and a join to a full channel fails (search summary); the Large 3D setting raises a 3D channel to 2,000 participants, is enterprise-only (enabled through a support engineer), disables text in positional channels and display names, and removes the normal small 3D mode. — [Vivox large 3D channel settings](https://docs.unity.com/en-us/vivox-unity/developer-guide/channels/large-3d-channel-settings)
- Vivox warns against an "auditorium mode" (many participants at one point or at the same audible distance): poor performance and audio artifacts. — [Vivox large 3D channel settings](https://docs.unity.com/en-us/vivox-unity/developer-guide/channels/large-3d-channel-settings)
- High Fidelity argued that with many live speakers the 3D processing cannot all be done on the client: sources are combined at a mixer so each receiver gets one left/right stream with the position cue preserved. Audio was sent in ~10 ms chunks (240 samples), aiming at ~40 ms end to end, and the post claims 3,000 source/receiver pairs per server (search summary; older material, High Fidelity's blog post about its VR platform). — [High Fidelity: 3D audio for shared VR](https://highfidelity.com/blog/3d-audio-for-shared-vr-c0f5301cece2)
- Epic Online Services Voice: connections are between authenticated users and relayed through Epic's back-end servers; Unreal's `IVoiceChat` channels are EOS rooms (search summary). — [Unreal: voice chat with EOS](https://dev.epicgames.com/documentation/en-us/unreal-engine/voice-chat-with-epic-online-services)
- Discord Social SDK: lobbies hold up to 1,000 members but voice calls are recommended for about 25 members or fewer (larger needs a request to Developer Support); a client can be in several lobby calls at once (search summary). — [Discord: managing voice chat](https://docs.discord.com/developers/discord-social-sdk/development-guides/managing-voice-chat), [Discord: managing lobbies](https://docs.discord.com/developers/discord-social-sdk/development-guides/managing-lobbies)

**(e) Peer-to-peer**
- Dissonance's WebRTC integration can run a fully peer-to-peer session that needs only a very lightweight session server carrying no voice (search summary). — [Dissonance quick start: pure P2P](https://dissonance.readthedocs.io/en/latest/Basics/Quick-Start-PureP2P.html)
- General WebRTC behaviour: a direct connection negotiates local and STUN-discovered public addresses, so peers learn each other's IP; only when media goes through a TURN relay does the remote peer see the relay's address instead (search summary of a general WebRTC explainer). — [GetStream: WebRTC IP leaks](https://getstream.io/blog/webrtc-ip-leaks/)

### Inferences
- For a world hosted by several server processes, pattern (a) in its literal form (the host that simulates the speaker relays the audio) breaks at a boundary: the listener may be connected to another host. The patterns that survive are a voice service that is separate from the simulation hosts and is fed positions or subscription decisions by them (b/d).
- LiveKit's server `updateSubscriptions` is the documented hook for "one big room, game server decides": clients join with auto-subscribe off and a trusted process sets each listener's track list. Nothing in the page I read says a client with a normal token is prevented from subscribing itself, so the token's permissions need checking separately (see Gaps).
- A grid of rooms (Dissonance) is the simplest continuous-world mapping but its cell size is tied to the audible range, and it gives a hard cut-off unless the client's attenuation curve reaches zero at the same range (Dissonance says so itself, section 3).
- Vivox's and Odin's position input comes from the client SDK in the documented flow. That is a trust decision: a modified client could report a false position to listen elsewhere (section 4).
- Simple Voice Chat's per-packet linear scan is fine for a Minecraft server's population and would need a spatial index (or the sim's existing interest grid) at MMO populations: 50 packets per second per speaker times all players.

### Gaps
- No primary source found for how Fortnite, LEGO Fortnite, PUBG, Rust, DayZ, Sea of Thieves, Star Citizen or EVE implement proximity voice internally. Fortnite's proximity chat is only documented as a creator-facing feature (section 2).
- CrewLink / BetterCrewLink (Among Us) and Lethal Company (reported to use Dissonance): my search found no primary source on their topology, scale limits or IP exposure. Not cited; if the report needs them, they need a dedicated lookup of the BetterCrewLink repository and README.
- Steam Voice (Steamworks voice API): not researched.
- No published case study of a shipped game using LiveKit for proximity voice was found; LiveKit's site names a "Portals" case study that I did not read.
- Whether Vivox mixes on its servers or on the client is not stated on the pages read.
- Dolby.io spatial: not researched (and its product status in 2026 was not checked).

## 2. Published details from specific implementations

### Takeaway
Simple Voice Chat is the best-documented end-to-end example (open source): a per-player AES key handed over the already-authenticated game connection, 48 kHz Opus in 20 ms frames over UDP, server-side range filtering, 48-block default range. Vivox publishes the clearest attenuation parameters (32 m audible, 1 m conversational, inverse rolloff by default).

### Cited Findings

**Simple Voice Chat (Minecraft)**
- Server defaults: `port` 24454 (UDP), `max_voice_distance` 48, `whisper_distance` 24, `codec` VOIP (alternatives AUDIO, RESTRICTED_LOWDELAY — Opus application modes), `mtu_size` 1275 bytes, `keep_alive` 1000 ms, `enable_groups` true, `allow_recording` true, `spectator_interaction` false, `spectator_player_possession` false, `force_voice_chat` false, `login_timeout` 10000 ms, `broadcast_range` -1 (falls back to the voice distance), `tcp_rate_limit` 16 packets/s over the Minecraft connection, `voice_host` blank (an address clients are told to use). — [server config wiki](https://modrepo.de/minecraft/voicechat/wiki/server_config)
- Key hand-over: the client requests a secret over a Minecraft plugin channel; the server creates a `ConnectionSecret` for that player UUID and answers with a `SecretPacket` carrying the secret, a connection id, the voice port, the server config and the voice host. A second request from the same player is ignored. Read from source. — [ServerVoiceEvents.java](https://github.com/henkelmax/simple-voice-chat/blob/26.3/common/src/main/java/de/maxhenkel/voicechat/voice/server/ServerVoiceEvents.java)
- Encryption: 16-byte random secret (AES-128), cipher `AES/GCM/NoPadding`, 12-byte random IV per packet, 128-bit tag. Read from source. — [Secret.java](https://github.com/henkelmax/simple-voice-chat/blob/26.3/common/src/main/java/de/maxhenkel/voicechat/voice/common/Secret.java)
- UDP datagram layout: a magic byte `0xFF`, the connection id (a UUID, in clear) and the encrypted payload; the server looks up the secret by connection id and silently drops packets with an unknown id or a failed decryption. Read from source. — [NetworkMessage.java](https://github.com/henkelmax/simple-voice-chat/blob/26.3/common/src/main/java/de/maxhenkel/voicechat/voice/common/NetworkMessage.java)
- UDP address check: after `AuthenticatePacket` the server sends an `AuthenticateAckPacket` holding a nonce (HMAC-SHA256 over connection id and source address, keyed with a 32-byte per-boot key) and accepts the `ConnectionCheckPacket` only with that nonce from the same address — "a client can only connect from an address it can receive packets at". Read from source. — [Server.java](https://github.com/henkelmax/simple-voice-chat/blob/26.3/common/src/main/java/de/maxhenkel/voicechat/voice/server/Server.java)
- Audio format: 48,000 Hz sample rate, frame size `(48000/1000)*20` = 960 samples = 20 ms, so 50 packets per second per speaker. Read from source. — [AudioUtils.java](https://github.com/henkelmax/simple-voice-chat/blob/26.3/common/src/main/java/de/maxhenkel/voicechat/voice/common/AudioUtils.java)
- Flood control: more than 100 voice packets per second from one player removes the connection and its secret at once and kicks the player ("Kicked for exceeding packet rate limit"); oversize Opus payloads are dropped. Read from source. — [Server.java](https://github.com/henkelmax/simple-voice-chat/blob/26.3/common/src/main/java/de/maxhenkel/voicechat/voice/server/Server.java)
- Liveness: keep-alives every `keep_alive` ms; a connection that has not answered for 10× that interval is dropped together with its secret. Read from source. — [Server.java](https://github.com/henkelmax/simple-voice-chat/blob/26.3/common/src/main/java/de/maxhenkel/voicechat/voice/server/Server.java)
- Routing: a force-muted or force-disabled sender is dropped on the server. A sender in a group sends a `GroupSoundPacket` (non-positional) to group members and, if the group is "open", also a proximity packet; receivers in an "isolated" group do not get proximity audio from outside; members of the same group are skipped in the proximity broadcast (no double audio). Read from source. — [Server.java](https://github.com/henkelmax/simple-voice-chat/blob/26.3/common/src/main/java/de/maxhenkel/voicechat/voice/server/Server.java)
- Packet kinds to listeners: `PlayerSoundPacket` (sender id, whisper flag, distance — the client places it at the entity it already knows), `LocationSoundPacket` (explicit position, used for spectators) and `GroupSoundPacket`. Read from source. — [Server.java](https://github.com/henkelmax/simple-voice-chat/blob/26.3/common/src/main/java/de/maxhenkel/voicechat/voice/server/Server.java)
- Features listed by the project: push to talk and voice activation, RNNoise suppression, automatic gain, OpenAL 3D sound, password-protected groups, per-player volume, recording with separate tracks, Velocity/BungeeCord/Waterfall proxy support, an add-on API. It also states: "The voice chat is encrypted, but we don't guarantee the security of it." — [GitHub README](https://github.com/henkelmax/simple-voice-chat)

**Plasmo Voice (Minecraft)**
- Whisper distance is half the current proximity distance (the percentage is configurable through the whisper add-on); a third-party guide shows a configurable list of selectable proximity distances in blocks; a separate add-on makes wardens and sculk sensors react to proximity voice (search summary). — [Plasmo Voice on Modrinth](https://modrinth.com/mod/plasmo-voice), [pv-addon-whisper](https://www.curseforge.com/minecraft/mc-mods/pv-addon-whisper/install)

**Vivox**
- `Channel3DProperties` defaults: `AudibleDistance` 32 ("the maximum distance away from a speaker that a listener can hear the speaker and receive their text messages"), `ConversationalDistance` 1 (inside it the voice stays at its original volume), `AudioFadeModel` `InverseByDistance`, `AudioFadeIntensityByDistance` 1.0. Default units are metres. — [Vivox positional channel properties](https://docs.unity.com/ugs/en-us/manual/vivox-unity/manual/Unity/developer-guide/channels/positional-channel-properties)
- Guidance: `0 <= ConversationalDistance <= AudibleDistance`; with the inverse model, to fade to near zero at the edge, `AudibleDistance >= 32 × ConversationalDistance ÷ AudioFadeIntensityByDistance`; with `ExponentialByDistance`, intensity ≈ `3 ÷ (1 + 1.75 × log10(ConversationalDistance))`. — [Vivox positional channel properties](https://docs.unity.com/ugs/en-us/manual/vivox-unity/manual/Unity/developer-guide/channels/positional-channel-properties)
- Positions are reported by the game client with `Set3DPosition`; Vivox recommends 2–4 position updates per second (search summary). — [Vivox positional channel configuration](https://docs.unity.com/en-us/vivox-unity/developer-guide/channels/positional-channel-configuration)
- When using positional and non-positional channels together, join the positional one first. — [Vivox positional channels](https://docs.unity.com/ugs/en-us/manual/vivox-unity/manual/Unity/developer-guide/channels/positional-channels)
- Vivox in the wild: V Rising's dedicated servers offer proximity voice through Vivox; the Kyber mod platform (Star Wars Battlefront II) uses Vivox with one channel per game-server id, positions updated by the client and ranges set server-side (search summary). — [V Rising mod wiki: voice chat](https://wiki.vrisingmods.com/user/voice-chat.html), [Kyber docs: voice chat](https://www.mintlify.com/ArmchairDevelopers/Kyber/features/voice-chat)
- Pricing signal: Modulate's primer says Vivox charges for games above 5,000 peak concurrent users (search summary; a competitor's blog — verify against Unity's price page). — [Modulate: VoIP for gaming 101](https://www.modulate.ai/blog/voip-for-gaming-101-part-1)

**Mumble**
- Client-side attenuation settings: full volume inside the minimum distance, falling to the minimum volume at the maximum distance; "bloom" controls how much directional audio spreads into other directions (search summary). — [Mumble audio settings](https://www.mumble.info/documentation/user/audio-settings/)
- Community starting values: Valheim guides use 1 m minimum / 50 m maximum / 0% minimum volume; a GTFO guide uses 4 m / 70 m / 35% bloom (search summary; community values, not defaults). — [Valheim PositionalAudio mod](https://thunderstore.io/c/valheim/p/jrobsonchase/PositionalAudio), [GTFO proximity chat guide](https://modding.pages.dev/GTFO/Proximity-Chat/Mumble-Setup/Configuring-Mumble/Positional-Audio-Settings)

**Roblox**
- Default voice (without the new audio API) uses a quadratic rolloff from 7 to 80 studs; with the audio API, `AudioEmitter:SetDistanceAttenuation(curve)` takes a table of distance → volume keys and falls back to an inverse curve when none is given (search summary). — [Roblox AudioEmitter reference](https://create.roblox.com/docs/reference/engine/classes/AudioEmitter.md), [DevForum: VoiceChat RollOffDistance](https://devforum.roblox.com/t/voicechat-rolloffdistance/3160460)
- Since January 2026 Roblox requires an age check (typically facial age estimation) before any chat, voice included, worldwide where chat is available; users are sorted into six age groups (search summary). — [Roblox press release, 7 Jan 2026](https://www.businesswire.com/news/home/20260107986568/en/Roblox-Requires-Users-Worldwide-to-Age-Check-to-Access-Chat)

**VRChat**
- The default "voice distance far" is 25 m and world creators can lower it down to 0 (which mutes a player); falloff is roughly inverse-square with adjustments, and a low-pass filter starts acting at half of the far range (search summary). — [VRChat creator docs: player audio](https://creators.vrchat.com/worlds/udon/players/player-audio/)
- A community request asks for a default of about 10 m, arguing 25 m suits outdoor spaces, not indoor rooms (search summary). — [VRChat feedback](https://feedback.vrchat.com/udon/p/lower-the-player-voice-distance-far-default-from-25-to-10)

**Fortnite (Creative / UEFN)**
- Proximity chat is a setting of in-game voice channels for creator islands, lets players talk when near each other, is off by default and was announced as Early Access (search summary; announcement date not checked). — [Fortnite: introducing proximity chat](https://www.fortnite.com/news/introducing-proximity-chat-incorporate-new-social-interactions-in-your-fortnite-islands)

**Rust (the game)**
- Only community sources: a modding thread refers to voice range levels of 5/20/50/100 m; another says voice distance is "kind of clientside" and hard to limit from a server plugin; a paid plugin (VoiceLimiter) exists to control range (search summary; unverified forum posts). — [uMod thread: show voice range](https://umod.org/community/rust/35201-show-voicerange-through-plugin), [uMod thread: changing radius](https://umod.org/community/rust/8386-changing-radius-of-voice-chatlocal-text-chat), [Codefling VoiceLimiter](https://codefling.com/plugins/voicelimiter)

**Star Citizen**
- The game has in-game VOIP including proximity VOIP; a 2024 blog recap of CitizenCon says CIG wanted to improve its quality and reliability (search summary; a fan blog, not technical). — [CitizenCon 2954 recap](https://scopique.github.io/scopique_blog/posts/2024/10/22/citizencon-2954-a-social-universe/)

**LiveKit spatial tutorial (browser)**
- Example `PannerNode` settings: `distanceModel` "exponential", `refDistance` 100, `maxDistance` 500, `rolloffFactor` 2 (in the demo's pixel units), cones 360°; position changes smoothed with `setTargetAtTime` and a 0.02 time constant; a new track starts far away (x = 1000) so it is not heard at full volume before its real position arrives. — [LiveKit spatial audio tutorial](https://livekit.com/blog/tutorial-using-webrtc-react-webaudio-to-create-spatial-audio/)
- Browser pitfall: a remote MediaStream must also be attached to a hidden, muted `<audio>` element and played, or the WebAudio graph gets no audio; nodes must be disconnected on cleanup. — [LiveKit spatial audio tutorial](https://livekit.com/blog/tutorial-using-webrtc-react-webaudio-to-create-spatial-audio/)

### Inferences
- The Simple Voice Chat hand-over is the reusable idea for any game with an authenticated session: the game connection is the identity proof, the voice transport only needs a random per-session key and id handed over it. For an SFU the equivalent is a short-lived room token minted by the game backend.
- Simple Voice Chat puts the connection id in clear in each datagram, so an on-path observer can tell which session speaks when, though not who it is without the mapping.
- Its default `broadcast_range` equals the voice distance (+1 block in code), so the server filter and the client attenuation share one radius and there is no hysteresis band.
- Vivox's defaults (32 m audible, 1 m conversational) follow from its own formula: 32 × 1 ÷ 1 = 32, the inverse curve reaching near zero exactly at the edge.

### Gaps
- Simple Voice Chat's Opus bitrate and its client-side attenuation curve were not read (client sources not fetched).
- Plasmo Voice's default distance, its handshake and its encryption scheme were not confirmed from a primary source.
- Roblox: no documentation found on per-server voice participant limits or on the voice transport.
- VRChat: no current documentation found on a maximum number of simultaneous voices; one old feedback entry says voice prioritisation was removed in 2019.
- DayZ, PUBG, Sea of Thieves, EVE Online, LEGO Fortnite: nothing technical found.
- Discord Social SDK: no proximity or per-user spatial feature found in the docs searched; a secondary source says its non-end-to-end-encrypted calls are being deprecated — not verified.

## 3. Tuning

### Takeaway
Published audible radii cluster between 25 and 50 m (VRChat 25 m, Vivox 32 m, Simple Voice Chat 48 blocks, Mumble community setups 50–70 m), with full volume inside 1–7 m and an inverse or exponential rolloff that must reach about zero at the cut-off radius. Hysteresis, fades and speaker caps are barely documented anywhere; they are left to the integrator.

### Cited Findings
- Audible radius: Vivox 32 m default — [Vivox properties](https://docs.unity.com/ugs/en-us/manual/vivox-unity/manual/Unity/developer-guide/channels/positional-channel-properties); Simple Voice Chat 48 blocks, whisper 24 — [server config wiki](https://modrepo.de/minecraft/voicechat/wiki/server_config); VRChat 25 m — [VRChat player audio](https://creators.vrchat.com/worlds/udon/players/player-audio/); Roblox legacy 80 studs with full volume inside 7 (search summary) — [DevForum](https://devforum.roblox.com/t/voicechat-rolloffdistance/3160460).
- Rolloff models in use: Vivox inverse (default) or exponential — [Vivox properties](https://docs.unity.com/ugs/en-us/manual/vivox-unity/manual/Unity/developer-guide/channels/positional-channel-properties); Roblox quadratic legacy / inverse default / free curve (search summary) — [Roblox AudioEmitter](https://create.roblox.com/docs/reference/engine/classes/AudioEmitter.md); VRChat roughly inverse-square plus a distance low-pass (search summary) — [VRChat player audio](https://creators.vrchat.com/worlds/udon/players/player-audio/); Mumble linear between a minimum and maximum distance down to a minimum volume (search summary) — [Mumble audio settings](https://www.mumble.info/documentation/user/audio-settings/).
- Edge behaviour: Dissonance by default cuts voice off abruptly at the edge of range; to fade, the playback AudioSource's attenuation curve must approach zero at the same range as the broadcast trigger, and the receive range must exactly match the broadcast range. — [Dissonance proximity chat tutorial](https://placeholder-software.co.uk/dissonance/docs/Tutorials/Proximity-Chat.html)
- Join pop: start a new source far away / silent until its first real position arrives, and smooth position updates. — [LiveKit spatial audio tutorial](https://livekit.com/blog/tutorial-using-webrtc-react-webaudio-to-create-spatial-audio/)
- Block-list leak at subscribe time: Vivox recommends sending block lists at login, because blocking on the `ParticipantAdded` event lets some initial audio through. — [Vivox large 3D channel settings](https://docs.unity.com/en-us/vivox-unity/developer-guide/channels/large-3d-channel-settings)
- Position update rate: Vivox 2–4 per second (search summary) — [Vivox positional channel configuration](https://docs.unity.com/en-us/vivox-unity/developer-guide/channels/positional-channel-configuration); Odin at most 10 per second (search summary) — [Odin Unreal reference](https://www.4players.io/odin/ai-training/unreal/reference/).
- Whisper / range modes: Simple Voice Chat has a whisper flag in the microphone packet and the server picks 24 instead of 48 blocks (read from source) — [Server.java](https://github.com/henkelmax/simple-voice-chat/blob/26.3/common/src/main/java/de/maxhenkel/voicechat/voice/server/Server.java); Plasmo whisper is half the proximity distance (search summary) — [Plasmo Voice](https://modrinth.com/mod/plasmo-voice); Rust reportedly has 5/20/50/100 m range levels (search summary, community) — [uMod](https://umod.org/community/rust/35201-show-voicerange-through-plugin).
- Separate channels: Simple Voice Chat groups are non-positional, password-protected, and come as open / isolated variants that decide whether proximity still applies (read from source) — [Server.java](https://github.com/henkelmax/simple-voice-chat/blob/26.3/common/src/main/java/de/maxhenkel/voicechat/voice/server/Server.java); Vivox pairs positional channels with non-positional "radio-like" ones — [Vivox positional channels](https://docs.unity.com/ugs/en-us/manual/vivox-unity/manual/Unity/developer-guide/channels/positional-channels); League of Legends reportedly uses two push-to-talk keys, one for party and one for team (search summary; news item) — [AlternativeTo news, Feb 2026](https://alternativeto.net/news/2026/2/league-of-legends-set-to-launch-long-awaited-global-team-voice-chat-feature).
- Occlusion in a voxel world: Sound Physics Remastered (same author as Simple Voice Chat) states it is optimised for use with Simple Voice Chat 2.x and has occlusion settings such as a block occlusion factor and occlusion variation; a third-party guide says voices pass through the same attenuation, occlusion and reverb as other sounds (search summary; the second claim is unverified). — [Sound Physics Remastered on Modrinth](https://modrinth.com/mod/sound-physics-remastered)
- Server-side occlusion alternative: the VoicePhysics plugin for Simple Voice Chat muffles voices behind walls "for every player" from the server, so listeners need no extra client mod (search summary). — [VoicePhysics on Hangar](https://hangar.papermc.io/Shamanalle/VoicePhysics)
- Presets per space: Vivox suggests different positional channel properties for outdoor areas, tight corridors, or a "cocktail party" effect. — [Vivox positional channels](https://docs.unity.com/ugs/en-us/manual/vivox-unity/manual/Unity/developer-guide/channels/positional-channels)
- Activation: Simple Voice Chat offers both push to talk and voice activation; Fortnite's proximity chat is off by default (search summary). — [Simple Voice Chat README](https://github.com/henkelmax/simple-voice-chat), [Fortnite announcement](https://www.fortnite.com/news/introducing-proximity-chat-incorporate-new-social-interactions-in-your-fortnite-islands)

### Inferences
- None of the sources read documents a subscribe/unsubscribe hysteresis band. The pieces that are documented imply one is needed: Dissonance's hard cut at the edge, Vivox's initial-audio leak at participant-added, and Simple Voice Chat's separate `broadcast_range` knob (deliver further than the audible distance). A workable rule is: deliver (subscribe) out to a radius somewhat larger than the audible radius, unsubscribe at a still larger one, and let the client's curve reach zero at the audible radius, so the transport edge is never audible. The exact margins are a design choice with no published reference values.
- Occlusion done on the listener's client (Sound Physics style) is cosmetic: the audio still arrives. Occlusion done on the server (VoicePhysics style) can also be a privacy property, but costs a ray or path query per speaker–listener pair.
- A top-N speaker cap is not documented by any of these products; Vivox's warning about many participants at the same audible distance is the only published sign that crowd density is a real load problem.

### Gaps
- No published numbers for hysteresis margins, fade times, or maximum simultaneous audible speakers.
- Default activation mode (push to talk vs voice activation) per game: not found in primary sources.
- How Sound Physics Remastered applies occlusion to voice internally was not read from its source.

## 4. Security and privacy

### Takeaway
The documented safe pattern is: the game connection authenticates the player and hands out a per-session voice credential, a server decides per packet who receives audio, and clients never connect to each other. Products where the client reports its own position or chooses its own subscriptions leave eavesdropping and position inference open unless the game server takes that decision over.

### Cited Findings
- Server-decided audibility: Simple Voice Chat sends a speaker's audio only to players inside the range computed on the server from server-side positions; clients send no positions and no subscription requests. Read from source. — [Server.java](https://github.com/henkelmax/simple-voice-chat/blob/26.3/common/src/main/java/de/maxhenkel/voicechat/voice/server/Server.java)
- Speaker identity cannot be chosen by the client: the server derives the sender from the connection whose secret decrypted the datagram and writes the sender UUID into the outgoing sound packet itself. Read from source. — [NetworkMessage.java](https://github.com/henkelmax/simple-voice-chat/blob/26.3/common/src/main/java/de/maxhenkel/voicechat/voice/common/NetworkMessage.java), [Server.java](https://github.com/henkelmax/simple-voice-chat/blob/26.3/common/src/main/java/de/maxhenkel/voicechat/voice/server/Server.java)
- Source-address proof against spoofed UDP: HMAC nonce bound to connection id and address (section 2). — [Server.java](https://github.com/henkelmax/simple-voice-chat/blob/26.3/common/src/main/java/de/maxhenkel/voicechat/voice/server/Server.java)
- Flood control: 100 voice packets/s cap with immediate secret removal and kick; 16 packets/s cap on the control channel. — [Server.java](https://github.com/henkelmax/simple-voice-chat/blob/26.3/common/src/main/java/de/maxhenkel/voicechat/voice/server/Server.java), [server config wiki](https://modrepo.de/minecraft/voicechat/wiki/server_config)
- Server-enforced mute: a force-muted player's packets are dropped at the server, not at listeners. Read from source. — [Server.java](https://github.com/henkelmax/simple-voice-chat/blob/26.3/common/src/main/java/de/maxhenkel/voicechat/voice/server/Server.java)
- The author's own caveat: "The voice chat is encrypted, but we don't guarantee the security of it." — [Simple Voice Chat README](https://github.com/henkelmax/simple-voice-chat)
- Client-reported position: in the Kyber/Vivox integration the client updates its own position in the Vivox SDK; Odin's position is likewise sent by the client (search summaries). — [Kyber docs: voice chat](https://www.mintlify.com/ArmchairDevelopers/Kyber/features/voice-chat), [Odin Unreal C++ guide](https://docs.4players.io/voice/unreal/guides/unreal-cpp-guide/)
- Vivox raises participant added/removed events when players enter or leave range. — [Vivox positional channels](https://docs.unity.com/ugs/en-us/manual/vivox-unity/manual/Unity/developer-guide/channels/positional-channels)
- Presence leak in rooms: Discord's lobby member list can show who is in voice even to a user who has not joined the call (search summary). — [Discord: managing voice chat](https://docs.discord.com/developers/discord-social-sdk/development-guides/managing-voice-chat)
- IP exposure: direct WebRTC connections expose peers' addresses; relaying hides them at the cost of no longer being peer to peer (search summary). — [GetStream: WebRTC IP leaks](https://getstream.io/blog/webrtc-ip-leaks/)
- An open-source RTS engine's design docs choose voice routed through the room server explicitly to keep players' IP addresses private, and team-only voice by default during a match so strategy does not leak (search summary; a design document, not a shipped game). — [Iron Curtain design docs: text chat and VoIP](https://iron-curtain-engine.github.io/iron-curtain-design-docs/decisions/09g/D059/D059-overview-text-chat-voip-core.html)
- A US patent describes a voice server kept completely separate from the game server "for privacy", with proximity clusters deciding channel membership (search summary; a patent claim, not an implementation). — [US 11547942](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/11547942)

### Inferences
- Range enter/leave events and "who is in the room" lists are a radar: a listener learns that a named player is within N metres even when that player is silent and unseen (behind terrain, underground in a voxel world). A design that cares about this should reveal a speaker's identity only while audio from them is actually being delivered, and should not expose a roster of in-range participants.
- One big SFU room has the same problem at the signalling level: participant lists and track-published events normally reach every member. Smaller rooms (per zone / grid cell) or a server-side forwarder in front of the SFU limit what a client can enumerate.
- With client-reported positions (Vivox/Odin default flows), the game server should be the one that submits positions, or the voice service must be told audibility directly; otherwise a modified client can place its "ears" anywhere.
- If client subscription requests are possible at all (LiveKit `setSubscribed`), the token must not grant free subscription, or the server-driven filter is advisory only. I did not verify which LiveKit permission expresses this (Gaps).

### Gaps
- LiveKit: how to prevent a client from subscribing itself (track subscription permissions, token grants, hidden participants) was not covered by the page read.
- No vendor documentation found on server-authoritative position input for Vivox (a server-to-server position API).
- No source found on speaker-identity hiding or on padding/traffic-analysis concerns for game voice.

## 5. Moderation and legal

### Takeaway
A game with voice between strangers that has UK users is in scope of the UK Online Safety Act (Ofcom published gaming-specific guidance in October 2025), and in the EU the DSA's baseline duties apply even to micro and small operators; recording voice for moderation is common at large publishers and brings consent and data-protection duties. This is a flag list, not legal advice.

### Cited Findings
- UK: Ofcom's gaming guidance says games in which users interact through voice or text chat (or profiles, avatars, objects) are likely in scope of the Online Safety Act; an illegal-content risk assessment is compulsory and should cover the 17 kinds of priority illegal content; for games Ofcom names terrorism, child sexual exploitation and abuse, and hate offences as the most likely, and cites research that voice and text chat in multiplayer games are used by grooming perpetrators (search summary — Ofcom's page refused my fetch, so the wording comes from the search digest and the law-firm notes). — [Ofcom: the Online Safety Act and gaming](https://www.ofcom.org.uk/online-safety/the-online-safety-act-and-gaming-know-the-risks-know-the-rules-know-how-to-comply), [Lewis Silkin note, Oct 2025](https://www.lewissilkin.com/insights/2025/10/24/ofcom-issues-guidance-about-online-safety-act-in-video-gaming-context-102lr5v)
- UK, children: without strong age assurance Ofcom expects a conservative assessment of children's exposure for all regulated user-to-user interactions, voice chat included (search summary). — [Lewis Silkin: OSA navigation for games, Mar 2026](https://www.lewissilkin.com/insights/2026/03/13/digital-commerce-creative-101-online-safety-act-navigation-for-the-video-games-industry)
- EU DSA: Article 19 exempts micro and small enterprises from the online-platform section (Section 3) except Article 24(3); Article 16 (notice and action) and Article 17 (statement of reasons) sit in the hosting section and apply at any size (search summary; the second source is a developer-oriented guide, not a regulator). — [DSA Article 19 text](https://www.springlex.eu/en/packages/dsa/dsa-regulation/article-19/), [sota.io DSA guide](https://sota.io/blog/eu-digital-services-act-2024-hosting-provider-developer-guide)
- Voice moderation by recording exists and is consent-based at Unity: under Unity Safe Voice the developer is the GDPR controller and responsible for obtaining consent, Unity the processor; its consent text says voice may be recorded and monitored for moderation and for training moderation models (search summary). — [Unity Safe Voice privacy overview](https://docs.unity.com/ugs/en-us/manual/safe-voice/manual/privacy/privacy-overview), [Unity Safe Voice consent](https://unity.com/kr/legal/biometric-consent)
- Riot's privacy notice says it may record and store voice and text chat for moderation and game integrity; Roblox frames voice data collection as consent by use (search summary via a third-party policy tracker — check the original notices). — [Riot notice, tracked copy](https://conductatlas.com/platform/riot-games/riot-games-privacy-notice/voice-and-text-chat-recording/), [Roblox policy, tracked copy](https://conductatlas.com/platform/roblox/roblox-privacy-policy/voice-chat-data-collection-and-retention/)
- ToxMod (Modulate) is the best-known proactive voice-moderation product; its vendor argues player reports alone miss most voice misbehaviour (search summary; marketing). — [Modulate compliance page](https://tox.modulate.ai/compliance)
- Age gating in practice: Roblox requires an age check before any chat since January 2026. — [Roblox press release](https://www.businesswire.com/news/home/20260107986568/en/Roblox-Requires-Users-Worldwide-to-Age-Check-to-Access-Chat)
- Default-off practice: Fortnite's proximity chat is off by default (search summary). — [Fortnite announcement](https://www.fortnite.com/news/introducing-proximity-chat-incorporate-new-social-interactions-in-your-fortnite-islands)
- Block lists: Vivox applies a block list server-side so blocked audio is stopped before it reaches the blocker, and wants it sent at login; Discord's SDK documents local muting of blocked players in lobby voice. — [Vivox large 3D channel settings](https://docs.unity.com/en-us/vivox-unity/developer-guide/channels/large-3d-channel-settings), [Discord: voice muting for blocked players](https://docs.discord.com/developers/discord-social-sdk/how-to/voice-muting-for-blocked-players)
- Server-enforced mute and a server switch for whether players may record: Simple Voice Chat (`allow_recording`, force-mute). — [server config wiki](https://modrepo.de/minecraft/voicechat/wiki/server_config)

### Inferences
- For a small EU-hosted operator the minimum set that the sources point to is: voice off or opt-in by default; a per-player mute and block that the server enforces (not only a local volume of zero); an in-game report path and a contact point for illegal-content notices (DSA Art. 16-style); a written risk assessment if UK players are admitted (OSA); a stated position on recording — either "voice is relayed live and never stored" in the privacy notice, or consent plus retention rules if clips are kept for reports; and an age stance (minimum age in the terms, or voice disabled for accounts not confirmed adult).
- Live voice that is never stored cannot be reviewed after a report, which is exactly why large publishers record; a middle path used by products like Safe Voice is recording only around a report, with consent.
- Whether live, unstored voice chat counts as "hosting" under the DSA is a legal classification question none of the sources answer.

### Gaps
- COPPA (US) and GDPR Article 8 age-of-consent specifics for voice: no regulator page was read; not cited.
- Whether voice data counts as biometric/special-category data when it is only relayed: one low-quality source asserted it for identification use; no authoritative source read.
- Ofcom's size-specific expectations for small or low-risk services, and the test for a "UK link" for a non-UK service, were not read (page fetch refused).
- Call of Duty's voice moderation specifics: not sourced in this pass.
- Platform (console / store) requirements for voice chat: not researched.
- I am not a lawyer; every point here needs legal review before it drives a decision.

## 6. Voice in a top-down commander / god-view mode

### Takeaway
I found no shipped RTS or colony-sim that documents proximity voice for body-less players; the only design material found uses room/team voice (non-positional), which matches the "group" channel that proximity mods ship alongside proximity.

### Cited Findings
- An open-source RTS engine's design documents specify All / Team / Whisper chat channels, voice that defaults to team-only during gameplay to avoid leaking strategy, and voice routed through the room server for IP privacy; they also note that OpenRA has no voice chat and the C&C Remastered Collection added basic lobby voice through Steam (search summary; design docs, not a shipped game). — [Iron Curtain: lobby communication](https://iron-curtain-engine.github.io/iron-curtain-design-docs/decisions/09b/D052/D052-lobby-communication.html), [Iron Curtain: text chat and VoIP](https://iron-curtain-engine.github.io/iron-curtain-design-docs/decisions/09g/D059/D059-overview-text-chat-voip-core.html)
- In a 0 A.D. forum thread a commenter argues that integrating a third-party tool (Discord, Mumble) is simpler than building voice into an RTS, and notes Mumble cannot route channels by team automatically (search summary; forum opinion). — [Wildfire Games forum](https://wildfiregames.com/forum/topic/39024-integrate-mumble-in-the-game-or-support-mumble-plugin)
- Spectator precedent in a proximity mod: Simple Voice Chat by default does not let spectators talk to players (`spectator_interaction` false); when enabled, a spectator's voice is emitted as a sound at the spectator camera's location, and `spectator_player_possession` lets a spectator talk to the player being spectated as a direct, non-positional stream. Read from source and config. — [Server.java](https://github.com/henkelmax/simple-voice-chat/blob/26.3/common/src/main/java/de/maxhenkel/voicechat/voice/server/Server.java), [server config wiki](https://modrepo.de/minecraft/voicechat/wiki/server_config)
- Non-positional group voice next to proximity is standard: Simple Voice Chat groups, Vivox non-positional channels, Discord lobby calls (about 25 members recommended). — [Simple Voice Chat README](https://github.com/henkelmax/simple-voice-chat), [Vivox positional channels](https://docs.unity.com/ugs/en-us/manual/vivox-unity/manual/Unity/developer-guide/channels/positional-channels), [Discord: managing voice chat](https://docs.discord.com/developers/discord-social-sdk/development-guides/managing-voice-chat)

### Inferences
- For several players co-managing one fortress, the documented precedents point to a non-positional room keyed on the fortress/team (the "group" channel), not proximity: there is no body to attach an emitter or ears to, and a free camera as the listening point would make the camera an eavesdropping device over anyone with a body.
- If commanders and embodied (adventure-mode) players share a place, Simple Voice Chat's spectator rules are the nearest precedent: body-less participants are silent to and deaf to proximity by default, with an explicit opt-in that emits their voice from a defined world point.
- Simple Voice Chat's open / isolated group flag is a ready model for the mixed case: an "open" fortress room lets a member with a body still be heard nearby; an "isolated" one keeps the room private.

### Gaps
- No primary documentation found for voice in Age of Empires IV, Company of Heroes, Stormgate, RimWorld multiplayer, Going Medieval, or Dwarf-Fortress-like co-op games; the pattern above rests on one design document and mod precedents.

## 7. Crossing server boundaries in seamless worlds

### Takeaway
I found no published description of how any seamless-world game (Star Citizen server meshing, SpatialOS titles, Dual Universe, MMO zone lines) carries proximity voice across a simulation boundary. What the documented products do show is that voice is normally a service separate from the simulation process, keyed by a channel name and fed positions — which is the property that makes a boundary irrelevant to it.

### Cited Findings
- Vivox positional channels are independent of game servers: a channel holds up to 2,000 participants (Large 3D), and positions come in through the SDK's `Set3DPosition`. — [Vivox large 3D channel settings](https://docs.unity.com/en-us/vivox-unity/developer-guide/channels/large-3d-channel-settings), [Vivox positional channel properties](https://docs.unity.com/ugs/en-us/manual/vivox-unity/manual/Unity/developer-guide/channels/positional-channel-properties)
- The common integration nevertheless scopes one voice channel to one game server: Kyber issues voice tokens for a channel per game-server id (search summary). — [Kyber docs: voice chat](https://www.mintlify.com/ArmchairDevelopers/Kyber/features/voice-chat)
- Odin rooms are likewise independent of the game's servers, with positions used for server-side culling inside a room and up to 64 positioned channels per room in Voice 2.0 (search summary). — [Odin core API](https://docs.4players.io/voice/core/api/functions/odin_room_update_position), [Odin Voice 2.0 blog](https://www.4players.io/blog/introducing-odin-voice-2.0)
- LiveKit's server API lets any trusted backend process change a participant's subscriptions in a room. — [LiveKit: receiving tracks](https://docs.livekit.io/home/client/receive/)
- Simple Voice Chat is the counter-example: voice lives in the game server process and the range query only considers players of the same level on that server; its proxy support (Velocity/BungeeCord) forwards a player to the voice endpoint of the backend server they are on, and `voice_host` lets the server tell clients a different address. — [ServerPlayerManager.java](https://github.com/henkelmax/simple-voice-chat/blob/26.3/common/src/main/java/de/maxhenkel/voicechat/voice/server/ServerPlayerManager.java), [Simple Voice Chat README](https://github.com/henkelmax/simple-voice-chat), [server config wiki](https://modrepo.de/minecraft/voicechat/wiki/server_config)
- Star Citizen: server meshing work continued into 2026 (a February 2026 CTO update on "quasi-dynamic" meshing); the only voice statement found is that in-game proximity VOIP exists and was unreliable as of 2024 (search summary; news and fan blog). — [MassivelyOP, Feb 2026](https://massivelyop.com/2026/02/06/star-citizen-cto-outlines-progress-on-server-meshing/), [CitizenCon 2954 recap](https://scopique.github.io/scopique_blog/posts/2024/10/22/citizencon-2954-a-social-universe/)
- A patent describes a voice server architecture kept separate from MMO game servers, with proximity clusters deciding who joins a voice channel (search summary; patent, not an implementation). — [US 11547942](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/11547942)

### Inferences
- For a world split across several host processes where two players can stand a metre apart on different hosts, the voice layer should have exactly one media session per client that is independent of which host simulates the player (a hand-off between hosts must not reconnect audio), and the audibility set must be computed from positions of both sides of the boundary. The game already has that data wherever it computes cross-boundary visibility (interest / halo data), so the audibility decision can be derived there and pushed to the voice service as subscription updates.
- Two workable shapes follow from the documented products: (1) one voice room per large area (larger than a host's territory, or the whole world while populations are small) with server-driven per-listener subscriptions; (2) a grid of rooms decoupled from host territories with neighbour-cell membership (Dissonance's model). Room-per-host is the one shape to avoid, because it recreates the seam.
- With several hosts each pushing subscription changes, one authority per listener is needed (the host that currently holds the listener decides what that listener hears) so that two hosts do not fight over one participant's subscription list during a hand-off.
- Browser clients constrain the media transport to WebRTC (or WebTransport plus a custom codec path), which favours an SFU-style service over a custom UDP relay like Simple Voice Chat's.

### Gaps
- No primary source on voice across server boundaries for Star Citizen, SpatialOS-based games, Dual Universe, New World, or EVE. This whole section's design guidance is inference from product documentation, not from a shipped seamless-world example.
- SFU limits that matter here (participants per room, cost of frequent subscription changes, whether a subscription change needs renegotiation) were not measured or read for LiveKit; one non-authoritative 2026 article recommends making subscription changes cheap control messages and recomputing audibility on a tick, which I did not verify.
