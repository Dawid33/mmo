# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Do not create git worktrees.** Work directly on `develop` in this checkout — including
for test runs, bisection/attribution checks, and subagent dispatches. Shared build caches
and the user's concurrent edits make extra checkouts more trouble than they're worth here.

## Project Overview

A voxel MMO in Rust with client/server architecture over QUIC, built around deterministic simulation and rollback netcode. The client is a Bevy app (rendering, windowing, input); the simulation crates (`game`, `server`) stay engine-agnostic — no Bevy, no windowing library.

**Direction (2026-10-20):** the game is becoming a **Dwarf Fortress–style** game on this multi-region engine — a huge world generated up front, players playing individual regions from a top-down commander camera, later travelling between regions (adventure / fortress mode); the MVP is fortress mode only. There is **no phased plan**: features are implemented piece by piece, roughly modelling Dwarf Fortress. Reference research (DF mechanics per system, MVP tiers, engine mapping) is `docs/superpowers/specs/2026-10-20-dwarf-fortress-research/` (start at `00-synthesis.md`); the phased transition plan next to it was rejected. `develop` was rebuilt on 2026-10-20 from `ds/oldMMOCode` (the MMO-era multi-region code, kept for region loading and traversal) + the stable toolchain, Blockbench model loading and the commander camera; a short-lived RTS pivot that collapsed the world to one 256 m map is preserved on branch `ds/rtsPivot` (its runtime `MapConfig` / `assets/map.ron` are there if wanted).

## Building and Running

Common tasks are wrapped in the root `justfile` — prefer it over retyping raw
`cargo` invocations. `just` (or `just --list`) shows every recipe;
the important ones are `just build`, `just run` (server + client together),
`just server`, `just client`, `just smoke`, `just test-one`, `just web`,
`just world-map`, and `just clippy`. **One toolchain for everything: a DATED nightly, pinned in `rust-toolchain.toml`**
(currently `nightly-2026-10-04` = 1.101.0-nightly, with `wasm32-unknown-unknown`, rustfmt and clippy) — builds,
tests, clippy, wasm and rust-analyzer all use it. Nightly is there only to keep `target/` small (it once reached 200 GB):
`.cargo/config.toml` `[unstable] embed-metadata = false` (`-Zembed-metadata=no`: crate metadata only in the `.rmeta`, not
duplicated into every `.rlib`) and nightly cargo's build-dir layout (intermediates under `target/<profile>/build/<crate>/<hash>/`,
final binaries still uplifted to `target/<profile>/`). The other size levers are stable: dev builds use `split-debuginfo = "unpacked"`
and dependencies keep `line-tables-only` debuginfo (`Cargo.toml`; `profiling` keeps full, packed debuginfo for perf), most
integration tests are ONE binary per crate (`tests/it.rs`, `--test it <file>::` — see Building and Running below), and builds whose
features change Bevy's own feature set build into `target/variants/<features>` (`just clean-variants`). No Cranelift `cargo-clif`;
bump the nightly date deliberately (then `just smoke` + `just determinism-wasm`), never to a floating `nightly`.
Machine-specific bits are overridable variables: `adapter=6700`
pins the client to a GPU (e.g. `just adapter=6700 run`; defaults to `$VOXEL_ADAPTER`, so exporting that once pins every recipe; `scripts/run.sh` defaults to `6700` instead — unpinned, this box lands on the NVK T600, which is ~30× slower on the voxel opaque pass than even the Intel iGPU).
**Keep the justfile in sync**: when you add, rename, or change how a build/run/test
command is invoked, update the corresponding recipe (and add a new one for any
workflow worth a one-word command) in the same change.

The raw commands the recipes wrap, for reference:

```sh
# Build everything (see scripts/build.sh)
cargo build --workspace --bins

# Run server + client together (see scripts/run.sh)
cargo run --bin server
cargo run --bin client
```

The server listens on `127.0.0.1:6466` (hardcoded in `crates/server/src/lib.rs`); the client connects to localhost and retries the connect for up to two minutes (`CONNECT_DEADLINE` in `crates/client/src/netcode.rs`), so start order no longer matters. `just run` / `just run-release` build both binaries first, start the server in the background, and stop it when the client window closes. **`just play` / `play-release` is the real game start: the client opens on the main menu** (New world → map generator → Play → the arrival world map; Load world; Exit), and spawns its own server per world — the `server` binary found next to the client executable (override `VOXEL_SERVER_BIN`), with `VOXEL_SINGLE_PLAYER=1` set so it exits when its last client leaves or its stdin closes, `VOXEL_WORLD_FILE` pointing at the world, and `VOXEL_SERVER_PORT` = a free UDP port the client picked (the server's QUIC port; unset = 6466), so a menu world runs alongside a dev server; a single-player server starts no WebTransport ingress and writes no cert-hash file, while dev servers keep 6466/6467. So `play` builds BOTH binaries with the same region/chunk dials and runs only the client. Worlds live in `worlds/<slug>/` (git-ignored): `terrain.world`, `world.json`, `preview.png` (legacy `worlds/default.world` still loads). The menu is skipped (straight to `127.0.0.1:6466`, as before) by `VOXEL_SKIP_MENU=1`, a NON-EMPTY `VOXEL_WORLD_FILE`, `RENDER_BENCH` or `VOXEL_AUTOPILOT`, and always on wasm; every recipe/script that starts a server itself (`run`, `client`, probes, profilers, `scripts/run.sh`) exports `VOXEL_SKIP_MENU=1`.

**World size** is a client-side dial (`crates/client/src/world_scale.rs`); the server only generates what clients subscribe to, so it shrinks both sides. `just world=tiny run` (1 simulated region, no LOD rings), `world=small` (1 region + one factor-2 ring), default `full` (at the test region size, 5×5 regions; the play recipes build 512 m regions, where `DEFAULT_NEAR_RADIUS` is 0, so `full` is a ONE-region window — plus the LOD rings out to `LOD_HORIZON_UNITS` = 1 km — 16 regions at the default size, ~1,060 LOD keys; the fog goes opaque there. The ring table is not widened for the bigger window: the near window is subtracted from it, so the factor-2 ring (bound 2) is entirely simulated terrain and factor 4 starts right outside it). The variable exports `VOXEL_WORLD`; `VOXEL_NEAR_RADIUS=0..3` and `VOXEL_LOD_RINGS=off|small|full|"2:2,4:4"` override its halves. The 32³-voxel render brick (`BRICK_VOXELS`) is baked into packed records, shaders and the LOD math — shrink the window, not that (the sim chunk is its own build dial, below). `just render-bench` honours it too (its readiness gates and JSON metadata follow the active scale; `RENDER_BENCH_LOAD_TIMEOUT_SECS` stretches the 120 s load budget for slow adapters). Use a small world for iteration on weak GPUs, but compare benchmark numbers only within one scale.

**Region size** is a BUILD-time dial, in BLOCKS (1 block = 1 m), so it keeps its meaning when the sim chunk size changes (the old chunk-denominated `VOXEL_REGION_CHUNKS` / `VOXEL_CELL_CHUNKS` now fail the build). The recipes that PLAY the game (`server`, `client`, `run`, `play`, the `-release` variants, `web*`, `diag`, `perf-capture`, `fly-probe`, `shuttle-probe`, `play-test`, the profilers `trace-chrome` / `trace-join` / `perf` / `perf-client` / `perf-server` / `profile-*` / `tracy-client`, and `cross-section`; `scripts/run.sh` too) default to 512 blocks (512 m regions, one-region near window), while tests, `check`, `clippy`, `render-bench` and raw `cargo` stay at 64 (64 m); an explicit `region_blocks=N` wins for every recipe. For experiments: `just region_blocks=128 run` compiles everything with `game::REGION_BLOCKS = 128` (2048-unit / 128 m regions instead of 1024 / 64 m; `crates/game/src/protocol.rs` parses `VOXEL_REGION_BLOCKS` with `option_env!`; `REGION_CHUNKS` / `REGION_BRICKS` / `REGION_SIZE` are derived from it). `REGION_BLOCKS_CHOICES` is 64, 128, 256 and 512 — each has its own `LOD_RING_TABLE` (re-cut to the same pixel budget and horizon) and checked fixtures; the tiling contract in `lod.rs` const-asserts a power of two and anything not in the list fails the build. 512 (8192 units / 512 m, since 2026-10-30) is played as a one-region window with a single factor-16 LOD ring out to the 1 km horizon. Old numbers for scale: a 256 m region was a 578 MiB raw snapshot and ~7 GB of server state for a 3×3 window at the old 2-block chunks (~50k chunks per region) — at 16-block chunks a 512 m region is 32×32 chunk columns; re-measure before quoting. The default lives in `.cargo/config.toml` `[env]` so raw `cargo`, rust-analyzer and `just` share one build fingerprint; switching recompiles `game` and its dependents (not Bevy or the forks). Server and client must be built with the same value — there is no connect handshake to refuse a mismatch. Every per-region cost scales with AREA (measured: region start 0.37 → 1.3 → 3.9 s and snapshot 40 → 161 → 578 MiB at 64 → 128 → 256 blocks), so compare numbers only within one region size; findings and the distance-based-window recommendation are in `docs/superpowers/specs/2026-09-20-region-size-investigation.md`. (Cell mode — island-sized regions loaded in cells, which allowed sizes up to 65536 — was removed 2026-10-30: every client simulated every active cell of its region, which cannot scale; regions are whole and players cross seams. `VOXEL_CELL_BLOCKS` now fails the build. Plan: `docs/superpowers/plans/2026-10-30-remove-cell-mode.md`.) Never write the region edge as a literal — derive from `REGION_BLOCKS` / `REGION_SIZE`; `REGION_CHUNKS` counts sim-chunk columns (4 at 64 m, 32 at 512 m) and `REGION_BRICKS` 32-voxel LOD/render bricks.

**Chunk size** is a BUILD-time dial too: `VOXEL_CHUNK_BLOCKS` (`game::CHUNK_BLOCKS`, parsed in `crates/game/src/block.rs`; `just chunk_blocks=N`, default 16 in `.cargo/config.toml` `[env]` and the justfile; legal: exactly 2 or 16 — the only sizes with pinned goldens — anything else fails the build). The **sim chunk** is `CHUNK_BLOCKS`³ blocks — 16³ = 16 m = 256 units (`CHUNK_UNITS`) by default — and is the unit that owns ONE entity, one rapier body and one collider set (block-scale + chisel-scale `Voxels`, or one cuboid when full); the 32³-voxel **brick** (`BRICK_VOXELS`, 2³ blocks) is the render/LOD unit: the server builds LOD from `Chunk::bricks()` views, and the client fans each sim chunk out to `BRICKS_PER_CHUNK_EDGE`³ (8³) brick entities (`renderer/bricks.rs`). Dense voxel arrays exist per brick only (`BrickView::voxels`, the test oracle `derive_voxels(chunk, brick)`), never per chunk. Every literal 32 must say which it is: `BRICK_VOXELS` or `CHUNK_UNITS`. 2 (the pre-2026-10-29 size, where chunk = brick) still builds and passes: hash goldens (`wasm_determinism`, `scene_hash_golden`) are pinned per chunk size, and the seam/slime `physics_goldens` are recorded at 16 and skipped at other sizes. Server and client must share the value; switching recompiles `game` and dependents and keys the worldgen cache separately. Spec: `docs/superpowers/plans/2026-10-29-chunk-size-increase-handoff.md`.

**Deployment (OpenTofu, not Terraform)** lives in `deploy/`: shared `modules/{platform,world}` and per-environment roots (`envs/local/{platform,world}`; `platform` must be applied before `world` — the world's Agones/CloudNativePG custom resources need the CRDs at plan time). The local environment is a single-node k0s in docker, like the planned production box: `just deploy-local` (creates the `mmo-k0s` node + applies both roots), `just deploy-local-plan`, `just kube <kubectl args>`, `just dev-cluster-down` / `dev-cluster-destroy` (the latter deletes the DB). It is for exercising the deployment, never the inner loop — `just run` stays native. The Fleet only appears with `-var game_image=…`; the server cannot run in a pod yet (binds 127.0.0.1, no image). Setup and the settings bare k0s needs: `docs/superpowers/specs/2026-09-22-local-deployment-environment-design.md`.

**Builds and tests are capped at 80% of cores** so they never take the whole desktop. A job count alone does not do it — each rustc runs multi-threaded codegen, and 16 jobs still saturated all 20 cores — so the justfile's `cap` variable prefixes every build/test/check/clippy invocation with `nice -n 10 taskset -c 0-<jobs-1>`, pinning the whole process tree (test binaries and their thread pools included) to the first `jobs` cores. `cargo run` and directly-launched binaries are never pinned, so the game and its perf numbers are unaffected. Tune with `just cpu_percent=50 build` or `just jobs=4 smoke`. **Raw `cargo` outside `just` is not pinned** (`.cargo/config.toml` only sets `jobs = -4`, and `cargo test` threads are uncapped) — go through `just`, or prefix `nice -n 10 taskset -c 0-15` yourself. Server-side, `LOD_BUILD_THREADS` sizes the LOD worker pool (default: a quarter of the logical cores, clamped 2..=6 — `crates/server/src/lod_workers.rs`; the server logs the resolved count at startup and `perf-capture` summaries show it).

The game crate has the rollback test suite: `cargo test -p game` (transaction/undo invariants in `tests/log_model.rs` and `tests/simple.rs`, seeded randomized rollback in `tests/random_ops.rs`, vendored-container inverse-op guarantees in `tests/hash_restore.rs`). Rollback correctness bar: `hash(before) == hash(after undo)`, bit-exact. The client has its own headless test suite: `cargo test -p client` (sim-bridge, coordinate conversion, interpolation, async chunk meshing, and full client/server convergence harnesses, run via `MinimalPlugins`/`AssetPlugin` with no window or GPU).

**Do not run the whole game / server / client suites as a routine check — they take far too long** (even the "quick" `just test` builds every game test module and a Bevy-sized client test binary). Verify a change with:

- `just test-one <crate> "<cargo test args>"` for exactly the tests the change touches, always naming the target so nothing else gets built (each crate's integration tests are one `it` binary, `tests/it.rs`, filtered by file name + `::`; the few files that need their own process — they flip the global `HASH_MODE`, pin the forged world, install a logger, run on wasm32 or are release perf gates — keep their own `--test <file>` target, listed at the top of `tests/it.rs`; a new test file that touches process-global state must get its own `[[test]]` too) — e.g. `just test-one game "--test it lod_streaming::pristine"`, `just test-one client "--lib world_scale::"`.
- `just test-threads` (~12 s warm) after touching boundary handoff, the `WorldManager` or `region_threads` — the region is the threading unit (one OS thread per running region; nothing inside a region is parallel), and these are the only tests where a player walks between regions on different threads. Two layers, both tagged slow so nothing else runs them: `crates/game/tests/handoff_schedule.rs` walks across a seam and through a region corner, there and back, under **seeded scheduling jitter** (`game::InlineSchedule` on the `InlineSpawner`: permuted tick order, inputs a tick late, missed ticks — a failure names a seed that replays exactly), and `crates/server/tests/threaded_world.rs` does the same walks on real OS threads, including waking a cold region on the production `with_generator` spawn path. Put scheduling-sensitive correctness in the seeded layer; keep real threads for plumbing. The client twin (`crossing_converges_under_late_region_scheduling` in `crates/client/tests/crossing.rs`) is a slow client opt-in.
- `just determinism-wasm` after touching sim math, the physics forks or anything hashed/serialized: the same scenes must end in identical state on native and wasm32 (node): `crates/game/tests/wasm_determinism.rs` pins a region scene (crc32 of its bincode bytes AND `game::state_hash`, asserted equal on both targets) and an underground dig (crc32 + state hash), and `crates/physics-next/tests/state_hash_wasm.rs` pins the forks' `StateHash` walk. The recipe installs the Cargo.lock-matched `wasm-bindgen-test-runner` under `target/tools` on first use. Behaviour across a physics-engine change is pinned separately by `just test-one game "--test it physics_goldens::"` (tolerance goldens; re-record only on purpose).
- `just smoke` as the general sanity check — **this is the default verification, and it is hard-limited to 60 s** (`smoke_timeout`; ~12 s warm): two game test binaries, the server lib tests, a *type-check* of the server's integration tests (all tagged slow, so nothing else notices them rotting), and a *type-check* of the client (lib + bin + tests). It never builds a client test binary, because that means a full Bevy codegen + link (many minutes cold). Running client unit tests is an explicit, slow opt-in (`just test-one client "--lib <filter>"`) — ask before doing it.

`just test` (whole quick suites) and `just test-full` (`--include-ignored`, minus the release-mode perf gates) still exist for a deliberate broad sweep; run them only when the user asks or a change is wide enough to need them, and say so first. Tests measured slower than 100ms are tagged `#[ignore = "slow: >100ms — run via just test-full"]`, which keeps them out of `smoke`, `test-one` and `just test`; tag any new test that takes >100ms the same way.

Bevy is pinned to `0.19.1` in the root `Cargo.toml`; Bevy's API surface moves fast between minor versions, so treat upgrades as a deliberate, tested migration rather than a routine bump — API drift (renamed types/traits, moved modules, changed system-set names) is a known hazard. The 0.18 → 0.19 migration (2026-09-22) is the worked example: the render graph is gone — custom passes are systems in the per-camera `Core3d` schedule ordered against Bevy's pass systems (`voxel_pull::gpu::add_near_gpu_systems`, `far_voxel::pass::far_voxel_pass`); `MeshPipelineViewLayouts` is built in `RenderStartup`, so pipelines that clone it are created there too; the view bind-group layout is keyed on many view features (fog, tonemapping, …), so custom mesh-view pipelines take their key from Bevy's `ViewKeyCache`, and the WGSL gates fog behind `DISTANCE_FOG`. The shader-validation tests compose against hand-written import STUBS, so an upstream WGSL signature change (0.19 added `frag_coord_xy` to `fetch_directional_shadow`) only shows at pipeline creation — after a Bevy bump, run `just pull-smoke` (self-screenshot of the production pull path) on a real adapter. `renderer::render_plugin()` disables wgpu's `EXPERIMENTAL_COOPERATIVE_MATRIX`, which NVK advertises but then fails `vkCreateDevice` with.

### WASM build (browser multiplayer)

The client also targets `wasm32-unknown-unknown`; in the browser the native
QUIC netcode is replaced by WebTransport (`crates/client/src/netcode_web.rs`):

```sh
cargo run --bin server   # quinn :6466 + WebTransport ingress :6467; writes
                         # assets/webtransport-cert-hash.json for the page
# From the repo root (so ./assets is served). The custom index adds a
# fullscreen canvas + download progress bar:
WASM_SERVER_RUNNER_CUSTOM_INDEX_HTML=crates/client/index.html \
  cargo run -p client --target wasm32-unknown-unknown   # opens via wasm-server-runner
```

Open `http://127.0.0.1:1334/` — connecting to the real server is the default,
and like the native client it retries for two minutes (`CONNECT_DEADLINE_MS` in
`netcode_web.rs`), re-fetching the cert hash each attempt, so the page may be
opened before the server is up.
Append `?world=tiny|small|full` to pick the world scale (the browser has no `VOXEL_WORLD`; default full — the debug wasm build is too slow for the full world), and `?offline` to opt into the embedded single-player world instead
(`crates/client/src/local_server.rs`, no server needed). Requires
`rustup target add wasm32-unknown-unknown` and `cargo install
wasm-server-runner`. See
`docs/superpowers/specs/2026-07-05-webtransport-netcode-design.md`.

### Profiling

Measure in **release** (`just diag`, `just client-release`, the `profiling` profile). The dev
profile is opt-level 1 and runs the hot loops ~2.5x slow, so an FPS number from `just client`
measures the build, not the game. And **always check which GPU you got**: this box exposes four
Vulkan devices (Intel iGPU, an NVIDIA T600 on the NVK driver, the RX 6700 XT, and llvmpipe
*software* rendering), and with no `WGPU_ADAPTER_NAME` wgpu chooses for you — pin it with
`just adapter=6700 …` and confirm against the `AdapterInfo` line in the log.

**Check the power source too.** On 2026-09-19 this laptop was fed by an ~88 W USB-C PD source
(`/sys/class/power_supply/ucsi-source-psy-*`) and the firmware clamped every core to ~400-700 MHz
under multi-threaded load (one busy P-core: 2-3 GHz of 4.6). Bursts run fast, then the clamp
bites, so anything multi-threaded (joins, region genesis, builds) measured several times slower
and noisier than the hardware allows — compare ratios, not seconds, until re-baselined on the
real adapter. Watch `scaling_cur_freq` under load to tell.

Text-emitting (readable in a terminal, pasteable into a bug report or an LLM session):

- `just perf-capture` — **the capture to hand to an analysis session.** Release server + one
  client, everything in one self-describing directory
  `target/perf-capture/<utc>-<adapter>-<world>/`: `summary.txt` (read first), `manifest.json`
  (git rev + dirty, profile, adapter asked for *and* selected, world scale, env knobs, host),
  both full logs, `rss.csv` (1 Hz RSS/threads/CPU), `gpu.csv` (1 Hz, no root: the client's own
  GPU engine time + GPU memory from DRM fdinfo — works on i915 and amdgpu, not NVK — plus sysfs
  whole-GPU counters) and `diag.txt` (the `diag` verdict + a per-dump timeline). It sets
  `DIAG=1` and `PERF_LOG=1`. `PERF_CAPTURE_SECONDS=90` closes the client by itself;
  `scripts/perf_capture_report.py <dir>` re-summarises an old capture.
- **The `[perf]` join timeline** (`crates/game/src/perf.rs`) is always on, in every log:
  `[perf] event=<name> t_ms=<ms since process start> key=value …` on both sides (client:
  `endpoint_up`, `connected`, `player_region`, `snapshot_received`, `region_loaded`,
  `bridge_region_spawned`, `first_update`, `first_near_mesh`, `near_meshing_drained`,
  `lod_requests_done`, `lod_all_received`, `connection_ready`, `load_progress` every 2 s until
  `world_ready`, and `main_stall` for any >8 ms call of the unbudgeted bridge systems; server:
  `client_connected`, `region_generate`, `region_genesis`, `snapshot_sent`). Volume is part of
  the contract — per process / region / batch, never per chunk, LOD key or frame; high-rate work
  goes into the periodic `[server]` counters line (`crates/server/src/perf.rs`: manager-thread
  worldgen, LOD latency vs build time, writer-task send time + `timeouts`, channel backlogs).
  `PERF_LOG=1` additionally raises the DEBUG `[client-budget]` / `[client] mispredicts/s` lines
  (their own `perf_budget` log target; `RUST_LOG` would replace Bevy's whole filter instead).
- `just fly-probe [seconds]` — **region-crossing repro, no human needed.** Release server + a
  client that, once `world_ready`, flies a straight line at fly-sprint (`VOXEL_AUTOPILOT=1`,
  `renderer/autopilot.rs`; `VOXEL_AUTOPILOT_SECONDS` closes it), crossing a region seam every ~3 s.
  Hands off the desktop: it sends sim inputs directly and enables body control with
  `InputEvent::FpsCam(true)` (sets fps-cam mode without the `SetFreeCam` that grabs the cursor),
  and mouse motion only reaches the sim while the window is focused AND holds the pointer. Per
  crossing it prints `[perf] event=region_crossing` (game thread: longest gap between home ticks,
  home ticks sat out by `stalled`, align steps, corrections, snapshot loads, `PlayerRegion`
  confirm latency) and `region_crossing_render` (worst frame, longest sim-pose hold; its
  `jump_max`/`back` straddle region-local frames at the flip — ignore those two). Pair
  `VOXEL_AUTOPILOT=1 VOXEL_AUTOPILOT_SECONDS=40` with the `trace_chrome` build for a per-system
  table of sustained flight (`scripts/trace_summary.py … --skip-ms 40000`).
  `just shuttle-probe [region|chunk] [seconds] [overshoot_m]` is the same benchmark for ONE
  boundary crossed back and forth (`VOXEL_AUTOPILOT=shuttle`): it flies to the first region
  seam (or a sim-chunk edge, `CHUNK_UNITS`) and reverses `overshoot` m past it each leg — every region leg is
  a handoff plus a near-window shift. The near window recentres only `WINDOW_RECENTER_MARGIN_M`
  (16 m) into a neighbouring region (`RegionCoords::recentered`); `VOXEL_WINDOW_MARGIN_M=0`
  restores recentring at the seam for A/B runs. Both probes end with `scripts/crossing_summary.py`
  (p50/p95/max per metric; flags a run that lost its GPU). Two runs have ended in a wgpu
  `DeviceLost` (once on the RX 6700, once on the Intel iGPU with nothing in dmesg) — cause
  unknown; both were runs that reloaded a row of regions on every crossing. Separately, the
  eGPU's Thunderbolt link logs ~1.2 s `pciehp: Timeout on hotplug command` stalls in dmesg,
  which line up with occasional ~2 s frames on the 6700.
- `just diag` — release client with `DIAG=1`, which adds Bevy's `RenderDiagnosticsPlugin`
  (`crates/client/src/renderer/diag.rs`, gated on the env var because the wgpu timestamp and
  pipeline-statistics queries cost a little). Every 2s (`DIAG_INTERVAL`) it dumps `fps`,
  `frame_time`, `entity_count` and, per render pass, `elapsed_gpu` / `elapsed_cpu` /
  `fragment_shader_invocations`; `scripts/diag_summary.py` then reduces the log to the
  **CPU-vs-GPU-bound verdict** — frame budget vs summed per-pass GPU time, plus the sorted pass
  table. GPU columns need Vulkan or DX12 — wasm records CPU time only. Note the client presents
  with vsync (Bevy's default `PresentMode::Fifo`), so a frame pinned at ~16.7ms is idle-waiting on
  present, not saturated; switch the `WindowPlugin` to `PresentMode::AutoNoVsync` to see real headroom.
- `just gpu-log` — `amdgpu_top` JSON sampled alongside a running client: GPU busy % from outside
  the process, as an independent check on the above. No rebuild needed.
- `just trace-chrome` — the follow-up when `diag` says CPU-bound. Builds with the `trace_chrome`
  feature (a tracing span per ECS system / extract step / render-graph node), writes a Chrome
  Trace Event JSON, and reduces it to a per-system table via `scripts/trace_summary.py`. The JSON
  only flushes on a clean exit, so close the window rather than Ctrl-C.
- `just trace-join` — the same capture reduced to ONLY its first `join_ms` (default 30 s): the
  load/join phase `trace-chrome` deliberately skips. Read the `max ms` column — one multi-second
  call is a main-thread stall. (`scripts/trace_summary.py <json> --until-ms N` on an existing trace.)
  `trace_summary.py` STREAMS the file (traces reach several GB — the rapier fork traces its solver
  internals, ~25 MB/s; never `json.load` one), sorts by **self time** (children excluded; schedule
  spans otherwise double count), prints a per-thread busy table, and takes `--thread <name>` and

## Workspace Layout

First-party crates (workspace members):

- `crates/macros` — Proc macro crate providing `#[rollback]` on the state module. Fields marked `#[undo(cell|map|slotmap)]` get tier-1 wrappers (`UndoCell`/`UndoMap`/`UndoSlotMap`) whose mutating methods log typed, exactly-invertible deltas automatically; `#[emit(insert = ..., remove = ...)]` derives renderer `GameDataUpdate`s from those deltas in both apply and undo directions. Unmarked fields stay `Undo<T>` (tier 2): mutate via `undo_scope()`/`undo()` closures that MUST be true inverses of the full serialized state (`hash(before) == hash(after undo)` is enforced at rollback time), or `change()` for snapshot-restore; `emit_on_undo()` registers compensating render events. Verification has three per-entry modes (`game::set_hash_mode`): `Full` (crc32 of the whole field's `StateHash` walk — the process-global default, used by tests/harnesses), `Delta` (digest of only the entry's mutation footprint), `Off`. The client and server binaries call `game::set_hash_mode_from_env()` at startup: `Off` unless the `HASH_MODE` env var (`off`|`delta`|`full`) overrides it (desync is caught by the periodic tick-interval state hash instead) — run with `HASH_MODE=delta` for per-entry footprint digests, or `HASH_MODE=full` when chasing a suspected footprint/capture gap (Full costs ~4.4 ms per block edit at 16-block chunks — a whole-chunk hash walk — so use it for desync hunts only). Hashing is the `StateHash` trait (`crates/state-hash` + `state-hash-derive`, derived on every state type and in the physics forks), never std `Hash` or serialized bytes. The vendored `slotmapd`/`rapier` forks expose exact LIFO inverses (`revert_insert`/`revert_remove`) because plain `remove(insert(x))` does NOT restore allocator state (free lists, versions/generations) — see `crates/game/tests/hash_restore.rs`. The macro generates all undo infrastructure (`Rollback`, `Undo<T>`, the wrappers, the log) at its invocation site and hardcodes `crate::GameDataUpdate`/`crate::serde` paths, so it must expand in the crate that defines the update enums — that's `game`. The design spec lives in `docs/superpowers/specs/2026-07-03-undo-api-redesign-design.md`.
- `crates/game` — Deterministic simulation shared by client and server, and the rollback-netcode state layer (absorbed from the former `crates/rollback`): `World`, `Region`, controllers (camera, rapier physics), plus `state.rs` (`GameData`, the `#[rollback]` invocation, `GameDataUpdate`), `voxel.rs` (`Chunk`: `CHUNK_BLOCKS`³ blocks + sparse chisel, 16 m by default; - `crates/worldgen` — Deterministic world generation: `generate_region(RegionCoords)` is a pure function from region coordinates to the full grid of chunk columns, which is what makes "cycle out = park, cycle in = restore-or-regenerate" safe. Terrain shape lives in `pipeline.rs`: Minecraft-weighted octave noises (`noise.rs` — first octave dominant, sd ~0.5; the splines are laid out on that distribution) → **islands in open sea** (`islands.rs`: a hashed quadtree of slots — 65.5 km roots (`ISLAND_MAX_CELLS`) splitting with `ISLAND_SPLIT_CHANCE`×`ISLAND_SPLIT_DECAY`^level down to 512 m, one island or open sea per leaf; `pipeline::island_terms` turns distance to the island centre over a coast-warped radius into the continents curve's input, so every island has a shelf and drop-off and the sea between islands is deep; land relief scales with island radius (`ISLAND_RELIEF_FRAC`). The root slot centred on the home region holds the SPAWN island, sized by the BUILD dial `just island=<cells>` (`VOXEL_ISLAND_CELLS`, 64 m cells, default 16 = 1 km, part of the cache key); `islands::island_info` finds its dry coastal spawn (nothing consumes it since cell mode's removal; regions spawn at the constant `PLAYER_SPAWN_X/Z`). The continents noise now only warps coasts; `FEATURE_SCALE` = 0.5 halves every macro wavelength) + erosion + a peaks-and-valleys fold of a domain-warped ridge noise for mountain ranges (`MOUNTAIN_OFFSET`, `RIDGE_WARP_M`); the fused `column()` must mirror the `#[cfg(test)]` `DensityFn` graph bit-for-bit. `tile_map::build_world_map` turns the forged world's rasters into the per-region `WorldMap` the server sends (recipe only: it reads `ForgedWorld` raster/sample APIs and never generates a region). **Look at the world with `just world-map`** (`examples/world_map.rs`: colour relief + 16-bit heightmap PNGs + land/height/slope stats into `target/world-map/`, one profile per pixel, e.g. `--span 65536 --size 2048`) after any tuning change, and re-run `examples/seed_scan.rs` to re-pick `WORLD_SEED`/spawn. **Forged worlds** (the direction for super regions — one finite, pre-generated world per pod, loading screen between them): `just forge-bench [size] [cell]` (wall time + max RSS of one forge into `target/forge-bench/`; the erosion step reuses its buffers via `erosion::StepScratch`); `just forge-proto` (`examples/forge_proto/`, offline, no determinism requirement) simulates a whole finite world — by default (`ForgeParams::default()`, also the server's missing-world forge and the tests) a 16 km **Continent** at 32 m cells (~5 s); layouts (`knobs::LAYOUT_*`) are One island / Archipelago / Island arc (sea all round, island metres unchanged) and Continent / Continents / Inland (`world::edges`: `sea_edges` of the four edges are sea, picked by seed, the rest LAND edges whose border cells are drainage outlets (`World::outlet`, routed like the sea by both routers) that follow the land just inside them DOWN, never up (`World::follow_land_edges`, `LAND_EDGE_OUTLET_SLOPE` below it — no lip, still a base level); belt uplift tapers over ~`LAND_EDGE_TAPER_M` (noise-varied) and belts running along a land edge are weakened, so no ridge forms parallel to it, noise scaled with `size_m / REFERENCE_SIZE_M`, mountain belts along convergent plate boundaries — `forge/plates.rs`: `plate_count` warped Voronoi plates with drift, belts on the clipped convergent edges plus `interior_ranges`; the world file stores them (`WorldArtifact::edges`, v4), and past a LAND edge `ForgedWorld::sample`/`patch` continue the border's own ground outward (the point clamped onto the edge — no cliff, no rivers or lakes, so LOD rings show land continuing) while past a SEA edge it is ocean at `OUTSIDE_HEIGHT_M`; a corner past both is sea) — geology-controlled stream-power erosion, orographic rain, drainage routed by a depression graph (`forge/routing_fast.rs`, Cordonnier 2019; the full Priority-Flood only for the first iteration of each level and the analysis), run coarse-to-fine (`forge::schedule`: knobs `coarse_levels` ×2-coarser levels run first — the coarsest `iters`, the final cell `refine_iters`, levels between half that — `World::upsample` carrying the state down; the 16 km / 32 m quality gate `just test-one worldgen "--test it -- --include-ignored forge_lib::forge_quality"` must pass), spill-level lakes, rivers as objects, `--search N` to rank seeds — and writes a world file `<stem>.world`; `forged.rs` reads it (`WorldArtifact` v4 (v3 + `edges`): quantised `u16` `QRaster`s for height/uplift/bedding/rain, lake bodies as cell runs, geology column, river reaches, spawn; zstd over row-delta rasters, ~1.1 B/cell; coast distance is recomputed on load; an older file is refused with `OldVersion` "re-forge this world", shown as "needs re-forge" in the main menu list; read/write is native-only) and serves it through the SAME `generate_region`/`coarse_tile` entry points when a world is installed. **The server serves a forged world by default**: `server::world_file` resolves `VOXEL_WORLD_FILE` — unset/empty = `worlds/default.world` (git-ignored; forged with `ForgeParams::default()` — the 16 km / 32 m continent — on first start if missing, a few seconds; the save is atomic (temp file + rename), an existing file is never overwritten, a corrupt one panics telling you to delete it), `procedural` = the noise world, anything else = that file (`just world_file=<path> run`) — and calls `forged::install` before worldgen first asks. Tests, tools and wasm never run the server, so they stay procedural unless `VOXEL_WORLD_FILE` is set (`forged::active()` keeps the env fallback: `procedural` = no world there too, relative paths from the repo root like the server). With a world the `seed` argument is ignored, the disk cache is keyed by the file's crc, a set-but-unreadable file panics rather than mixing worlds. Generated terrain is **whole blocks and half blocks only**: the surface is rounded to the nearest half block (`HALF_TEST_M`/`FULL_TEST_M` in `lib.rs`), and a half block is NOT a special block type — it is ordinary `ChiselData` holding one cuboid (`ChiselData::cuboid`), so it is voxel-editable like any chisel. A submerged surface block is always whole (a half block's empty upper half would be an air pocket). `examples/quantize_probe.rs` reports region cost + step walkability. Both paths build blocks from a `Patch` (column profile + topmost water block per column): forged patches interpolate the raster bicubically on the usual 4 m lattice, then carve river channels, levees and lake berms per point so water above sea level is contained (water surfaces snap to whole blocks). Forged column profiles are **unbounded** (`ColumnProfile::unbounded`: no density ramp, surfaces scanned in `FORGED_SCAN_TOP`/`BOTTOM` = 4096/−1024 blocks; procedural keeps the 320/−64 ramp band, bit-identical), the surface scan starts at the analytic `surface_y()`, and a forged coarse LOD cell column fills down to its lowest face neighbour's surface so steep faces have no gaps (procedural coarse tiles keep the soil-band fill). `just world-map --world <file>` renders a forged world exactly as the generator samples it; every height map (the minimap, the world map, the forge previews) colours land by the one ramp `tile_map::height_color` (to 3,500 m, snow above `SNOW_LINE_M`), and the tools' 16-bit heightmaps span −1,000…+3,600 m. `just cross-section [--world <file>] [--region X,Z] [--axis x|z] [--at <block>]` writes a vertical slice PNG of the generated ground (soil, rock layers, bedrock) and prints the centre column's strata. **Trees** (`trees/`): `skeleton(species, seed, age)` is a parametric recursive skeleton (trunk → limbs → branches, per-species `ShapeParams` in `SPECIES`, angles from the integer `SIN_TABLE`, fitted inside the species' crown radius and height; a younger skeleton is a prefix of an older one) and `rasterize` turns it into `TreeBlock`s (whole or voxel-masked `Log`/`Branch`, whole `Leaves`); look at one with `just tree-view --species oak|pine|birch --seed N --age N [--grid]` (front/side/top PNGs, or a 3×3 seed sheet, in `target/tree-view/`). `trees_in` places them order-independently on a `TREE_LATTICE_BLOCKS` lattice where the species' climate niche allows (no water, no crown across a region seam), and generated terrain writes them as `<sp>_log` / `<sp>_branch` / `<sp>_leaves` blocks (sp ∈ oak/pine/birch) carrying the tree in `Block.data` (`Block::with_tree(id, tree, limb)`: bits 0..18 the tree id — `tree_id()`, 0 = not a tree; placement's id is `lx mod 512 | (lz mod 512) << 9`, unique within any 256-cell neighbourhood — and bits 18..24 the limb — `limb()`: 0 for the trunk, else `(ordinal % 63) + 1` of the level-1 skeleton node it grows from (`TreeSkeleton::limbs`, stable as the tree grows); wood takes the lowest limb of the segments filling it, leaves their cluster's). Per-block props come from the manifest (`game::block_props()`: `is_solid` — leaves are not, so they have no collider; `is_cutout` — leaves draw alpha-cutout; `collider_scale` — wood collides on the half-block grid). Growth is not built. **Tuning the forge:** every tunable lives in one runtime table, `crates/worldgen/src/forge/knobs.rs` (its defaults ARE the tuning — they build ~2 km ranges on the 16 km continent and 2–2.5 km on the island, `max_peak_m` caps relief at 2,800 m (≤ 3,500), the geology column reaches `COLUMN_BOTTOM_S` = −5 km; CLI `--set <knob>=<value>`), and `just forge-ui` serves a local page (`serve.rs` + `ui.html`, std-only HTTP on 127.0.0.1:8787) with each knob as a slider and a live map preview — a change re-forges at 64 m cells in ~1.5 s; layers rivers/relief/geology/rain/before-erosion, press-and-hold for the previous render, "Copy as flags", "Save world file" (forges at 16 m). Coarse previews under-count lakes and peaks — check at 16 m before keeping a value. Unset, nothing changes — procedural tests never see it. Depends on `game` (not vice versa) — generation is injected into the `WorldManager` as a closure. `coarse_tile` point-samples one profile per LOD cell column for every block-scale-or-coarser factor (16/32 per region, 64/256 per tile; ~40× cheaper than generating the region, and exact at factor 16) — the cheap pristine-terrain base the server overlays authoritative regions onto. Water fills through `SEA_TOP_BLOCK`, so the sea surface is `SEA_LEVEL` = 1024 voxels, a multiple of every LOD cell: any-solid downsampling rounds surfaces up a cell, and a sea off that lattice shows as a wall at ring boundaries.

## Vendored Forks

`crates/rapier`, `crates/parry`, `crates/slotmapd` and `crates/block-mesh` are vendored, locally patched forks wired in via `[workspace.dependencies]` path overrides. Everything else (glam/`glamx`, `nalgebra` 0.35 and `simba` 0.10 inside rapier, `approx`, `ordered-float`) comes from crates.io — the old nalgebra/simba/approx/ordered-float forks were dropped in the rapier 0.36 switch (upgrade plan `docs/superpowers/plans/2026-09-22-rapier-035-upgrade.md`, decision D4), and glam is deliberately not forked.

- **rapier 0.36.0 / parry 0.31.1** (import commit `bb7d5b5`, pristine upstream). Every hunk that differs from upstream carries a `// mmo-fork:` marker (`grep -rn "mmo-fork" crates/rapier crates/parry`) and is pinned by a test in `crates/physics-next` (the forks' test crate; `just physics-next-upstream` runs upstream's own determinism/regression tests against the forks). Updating to a newer upstream is a re-import plus re-applying the marked hunks, not a version bump. The patches:
  - **Rollback.** The hybrid `StepJournal` (`pipeline/step_journal.rs`, `PhysicsPipeline::step_journaled`): first-touch capture of bodies/colliders in the set accessors plus per-tick clones of the island manager, narrow and broad phase, reverted exactly (`StepJournal::revert`; digests `pre_digest`/`revert_digest` for `HashMode::Delta`); the arena/set inverses the game's undo closures call (`alloc_state`/`revert_insert`/`restore_raw`/`pop_modified`); pipeline memo invalidation after a revert (`IslandManager::journal_reverts` epoch).
  - **`StateHash`** derives and hand impls on ~160 rapier/parry types (cached digests: the voxels content hash, sorted broad-phase pairs, island joint links); serde-skipped workspaces are `#[state_hash(skip)]`.
  - **Mass properties.** Fixed bodies skip the collider mass properties (their voxel shapes would otherwise go through std `acos`/`cos` in glamx `SymmetricEigen3`, a cross-target hazard), and a body-type change triggers the recompute.
  - **Shape casts and the character controller** (walking on voxel terrain): the voxels shape cast's search domain, internal-edge normals and resting contact without ray casts; grazing starts in the support-map cast; `QueryPipeline::cast_shape_on_continuous_surfaces` (flush seams are not edges), whose TOI ties are ranked blocking → least-opposing → lowest collider index instead of BVH traversal order; the KCC snap gate and flush-seam handling; the KCC `depenetrate: bool` gate (plan D7 — the game sets it `false` and keeps `movement::depenetration_lift`). Pinned also by `crates/game/tests/shape_cast_grazing.rs`, `walking_smoothness.rs`, `sunk_body.rs` and `physics_goldens.rs`.
  - **Kinematic sleep.** Upstream 0.36 put kinematic bodies to sleep at zero velocity despite `can_sleep(false)`; `RigidBodyActivation::update_energy` honours it (physics-next `kinematic_sleep.rs`).
  - Packaging: self-contained `Cargo.toml`s (upstream inherits from its own workspace).
- **Determinism** comes from upstream features, not patched math: `rapier3d`'s `enhanced-determinism` (simba on `libm`, glamx on `libm` + `scalar-math`); no `parallel`, no `simd8`, and no inherent `f32` transcendental in a sim path (use `libm::`). The rollback hash is our own `StateHash` trait (`crates/state-hash` + `state-hash-derive`): `f32` hashes canonical bits, `usize` as `u64`, so hashes agree on native and wasm32 (`just determinism-wasm` checks it). The game steps physics once per region tick at `dt` = `movement::TICK_DT` with `length_unit` = `movement::PHYSICS_LENGTH_UNIT` (16 = `UNITS_PER_METER`).
- **slotmapd** exposes exact LIFO inverses (`revert_insert`/`revert_remove`) the undo log needs; **block-mesh** (used by `game`, `client`, `worldgen` for meshing helpers) is not physics and was untouched by the switch.

Changes to simulation math anywhere in these forks can break determinism between client and server: run `just determinism-wasm` and the physics-next suite after touching them.

## Conventions

- Serialization over the wire is `bincode`, framed by `game::encode_packet` / `decode_packet` (`crates/game/src/protocol.rs`): one format byte, and packets above `PACKET_COMPRESS_THRESHOLD` are lz4-compressed (`lz4_flex`; a region snapshot goes 40 MiB → 0.9 MiB). Every transport edge — server writer + QUIC/WebTransport ingress, native client, wasm client — must use that pair; never call `bincode` on the wire directly. State hashing uses `crc32fast`.
- Cross-thread communication uses `crossbeam` channels (game loop ↔ network loop ↔ render loop); async (tokio) is confined to the QUIC networking edges.
- Editions are mixed intentionally: older crates are 2021, newer ones (`macros`, `worldgen`) are 2024.
- `TODO.md` tracks the current high-level direction (the Dwarf Fortress direction's next step, plus the multi-region follow-ups).
- The root `justfile` is the canonical set of build/run/test commands — use it, and edit it whenever the underlying commands change so it never drifts from reality.
