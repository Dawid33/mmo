# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Do not create git worktrees.** Work directly on `develop` in this checkout — including
for test runs, bisection/attribution checks, and subagent dispatches. Shared build caches
and the user's concurrent edits make extra checkouts more trouble than they're worth here.

## Project Overview

A voxel MMO in Rust with client/server architecture over QUIC, built around deterministic simulation and rollback netcode. The client is a Bevy app (rendering, windowing, input); the simulation crates (`game`, `server`) stay engine-agnostic — no Bevy, no windowing library.

**Direction (2026-10-20):** the game is becoming a **Dwarf Fortress–style** game on this multi-region engine — a huge world generated up front, players playing individual regions from a top-down commander camera, later travelling between regions (adventure / fortress mode); the MVP is fortress mode only. There is **no phased plan**: features are implemented piece by piece, roughly modelling Dwarf Fortress. Reference research (DF mechanics per system, MVP tiers, engine mapping) is `docs/superpowers/specs/2026-10-20-dwarf-fortress-research/` (start at `00-synthesis.md`); the phased transition plan next to it was rejected. `develop` was rebuilt on 2026-10-20 from `ds/oldMMOCode` (the MMO-era multi-region code, kept for region loading and traversal) + the stable toolchain, Blockbench model loading and the commander camera; a short-lived RTS pivot that collapsed the world to one 256 m map is preserved on branch `ds/rtsPivot` (its runtime `MapConfig` / `assets/map.ron` are there if wanted).

## Building and Running

Common tasks are wrapped in the root `justfile` — prefer it over retyping raw
`cargo` invocations. `just` (or `just --list`) shows every recipe;
the important ones are `just build`, `just run` (debug launch: straight into the embarked debug world),
`just server`, `just client`, `just smoke`, `just test-one`, `just web`,
`just world-map`, and `just clippy`. **One toolchain for everything: a DATED nightly, pinned in `rust-toolchain.toml`**
(currently `nightly-2026-10-04` = 1.101.0-nightly, with `wasm32-unknown-unknown`, rustfmt and clippy) — builds,
tests, clippy, wasm and rust-analyzer all use it. Nightly is there only to keep `target/` small (it once reached 200 GB):
`.cargo/config.toml` `[unstable] embed-metadata = false` (`-Zembed-metadata=no`: crate metadata only in the `.rmeta`, not
duplicated into every `.rlib`) and nightly cargo's build-dir layout (intermediates under `target/<profile>/build/<crate>/<hash>/`,
final binaries still uplifted to `target/<profile>/`). The other size levers are stable: dev builds use `split-debuginfo = "unpacked"`
and dependencies keep `line-tables-only` debuginfo (`Cargo.toml`; `profiling` keeps full, packed debuginfo for perf), most
integration tests are ONE binary per crate (`tests/it.rs`, `--test it <file>::` — see Building and Running below), and builds whose
features change Bevy's own feature set build into `target/variants/<features>` (`just clean-variants`). No Cranelift `cargo-clif`;
bump the nightly date deliberately (then `just smoke` + `just determinism-wasm`), never to a floating `nightly`.
**Compile-time levers (measured 2026-11-01)**: `.cargo/config.toml` turns on workspace feature unification (`resolver.feature-unification = "workspace"`), so `-p <crate>` builds (smoke, test-one) and root `--bin`/`--workspace` builds share ONE copy of every dependency instead of each building its own rapier→game→client and Slint→slint-ui chain; the Slint screens are generated into three crates (`slint-ui-game` ~4.4 MB of Rust, `slint-ui-frontend` ~5.9 MB, `slint-ui-tools` outside the game build; sizes after 2026-11-02's two codegen cuts — the widgets' `LayerView` no longer binds `visible` on its root, which made Slint force-inline it and re-emit its repeaters at every use, and the widgets are compiled Fortress-only, see `docs/superpowers/specs/2026-11-02-slint-codegen-size-investigation.md` — see `crates/slint-ui` below), each at dev opt-level 0 with `-Zthreads=8` (non-incremental, so safe there): a `.slint` edit costs ~35–42 s end to end instead of ~6 min (one 27 MB crate at opt-level 1: ~360 s; at opt-level 0 ~62 s) and the client then relinks in ~3 s; the `client` crate builds with `-Clto=off` (profile `rustflags`, nightly `profile-rustflags`) — local ThinLTO made a one-line edit re-optimise 242/256 incremental CGUs (~36 s → ~15 s). Don't add `-Zthreads` to incremental crates: it scrambles CGU reuse. Test builds keep their own copies of rapier → game → worldgen → server/client ON PURPOSE (worldgen's dev-dependency `rapier3d/profiler` splits them): tests build at region dial 64 and the play recipes at 256, and cargo fingerprints `VOXEL_REGION_BLOCKS` without keying artifacts on it, so one shared copy would recompile that chain on every `just smoke` ↔ `just run` switch — everything below rapier (Bevy, Slint, slotmapd) is shared. Measured 2026-11-02: a client edit rebuilds in ~15–18 s, a `game` function-body edit (client + server) in ~7 s.
Machine-specific bits are overridable variables: `adapter=6700`
pins the client to a GPU (e.g. `just adapter=6700 run`; defaults to `$VOXEL_ADAPTER`, so exporting that once pins every recipe; `scripts/run.sh` defaults to `6700` instead). Unpinned — or pinned to a name no present GPU matches, e.g. `6700` with the eGPU unplugged — the client no longer lands on the NVK T600 (~30× slower on the voxel opaque pass than even the Intel iGPU; `just run` was 8 fps there): `client::adapter_pick::pin_adapter` runs first in `main`, enumerates the adapters and sets `WGPU_ADAPTER_NAME` to the best by rank (discrete not on NVK > integrated > NVK > software); a name that is present is left alone.
**Keep the justfile in sync**: when you add, rename, or change how a build/run/test
command is invoked, update the corresponding recipe (and add a new one for any
workflow worth a one-word command) in the same change.

The raw commands the recipes wrap, for reference:

```sh
# Build everything (see scripts/build.sh)
cargo build --workspace --bins

# The embarked debug launch (`just run`, scripts/run.sh): the client spawns the server
cargo build --bin client --bin server && ./target/debug/client debug embarked
# A dev server on 127.0.0.1:6466 and a client connecting to it (`just server` + `just client`)
cargo run --bin server
VOXEL_SKIP_MENU=1 cargo run --bin client
```

The server listens on `127.0.0.1:6466` (hardcoded in `crates/server/src/lib.rs`); the client connects to localhost and retries the connect for up to two minutes (`CONNECT_DEADLINE` in `crates/client/src/netcode.rs`), so start order no longer matters. **Debug launches** (`crates/client/src/debug_launch.rs`): the client binary takes `client debug <preset> [--reset]` to skip the manual setup (a bare `client` = the main menu; a bad command line prints usage, exit 2; a debug launch wins over the `VOXEL_SKIP_MENU` bypass) — presets so far: `embarked`, which `just run` / `run-release` launch (`just run --reset`): a small world (`ForgeParams::default()`, 16 km / 32 m) in `worlds/debug-embarked/`, forged through the generator's `ForgeJob` on first run (progress on the starting screen, via `session::PreparingWorld`) and started like a menu world (its own server), then the arrival map's own requests embark automatically — `ReturnTo` the world's returnable (player-founded) site if there is one, else `Embark` the first civ's first ≤ 7 people on the legal tile nearest its first site (`choose_embark`); a world without history just plays the spawn region. **Two clients on one server, one fortress**: `just run-two` (`run_two_port=6476`) — client 1 runs the preset in fortress mode with `--port N` (its world's server on that fixed UDP port) and logs `[debug] embarked: fortress site=S`; then client 2 runs with `--join 127.0.0.1:N --adventure-at S` (no world/server of its own; sends `StartAdventure(S)`, so it plays the same fortress in Adventure mode); a `ReturnTo` refused `InUse` moves on to the next returnable fortress; closing client 1 ends both. The world AND its fortress are reused across runs (the server keeps the fortress in `terrain.history`); only `--reset` or deleting the directory starts over; an unloadable debug world (e.g. other region size) is refused with a pointer to `--reset`, never re-forged silently. Add further presets there. **`just play` / `play-release` is the real game start: the client opens on the main menu** (New world → map generator → Play → the arrival world map; Load world; Exit). The generator (`crates/client/src/frontend/generator.rs`) defaults to a 100 km (DF medium, 100,352 m) world at 16 m cells — `ForgeParams::default()` (server auto-forge, tests, bare `forge-proto`) stays the quick 16 km / 32 m Continent — with sizes 16/32/64/100 km labelled by an estimated forge time and the time + RAM estimate beside Play (`worldgen::forge::play::forge_estimate`, scaled from `just forge-bench` runs), the preview cell picked from the size (`play::preview_cell_for`, ≤ 512² cells; Advanced overrides it), only World cells whose estimate fits `play::MAX_PLAY_FORGE_RAM_BYTES` (12 GiB — the forge runs inside the client) offered per size (100 km: 16 / 32 m, no 8 m) and Play refused above that or half the machine's memory (`play::check_play_ram`), presets Continent (= defaults) / Continents / Inland / Temperate band / Frozen north / Tropical / Great ranges / Island / Archipelago / Island arc / Highlands / Lowlands / Dry / Wet (`forge/presets.rs`; `forge-proto --preset <name>`), and Play forging through `play::forge_to_file` into the world's staging dir: Cancel stops within one erosion iteration and leaves no file, and a forge panic ends as an error, never a hang, and spawns its own server per world — the `server` binary found next to the client executable (override `VOXEL_SERVER_BIN`), with `VOXEL_SINGLE_PLAYER=1` set so it exits when its last client leaves or its stdin closes, `VOXEL_WORLD_FILE` pointing at the world, and `VOXEL_SERVER_PORT` = a free UDP port the client picked (the server's QUIC port; unset = 6466), so a menu world runs alongside a dev server; a single-player server starts no WebTransport ingress and writes no cert-hash file, while dev servers keep 6466/6467. So `play` builds BOTH binaries with the same region/chunk dials and runs only the client. Worlds live in `worlds/<slug>/` (git-ignored): `terrain.world`, `world.json`, `preview.png` (legacy `worlds/default.world` still loads). The menu is skipped (straight to `127.0.0.1:6466`, as before) by `VOXEL_SKIP_MENU=1`, a NON-EMPTY `VOXEL_WORLD_FILE`, `RENDER_BENCH` or `VOXEL_AUTOPILOT` (never on wasm, which opens on its own Join-server menu, below); every recipe that connects to a dev server (`client`, probes, profilers) exports `VOXEL_SKIP_MENU=1`.

**World size** is a client-side dial (`crates/client/src/world_scale.rs`); the server only generates what clients subscribe to, so it shrinks both sides. `just world=tiny run` (1 simulated region, no LOD rings), `world=small` (1 region + one factor-2 ring), default `full` (at the test region size, 5×5 regions; the play recipes build 256 m regions, where `DEFAULT_NEAR_RADIUS` is 0, so `full` is a ONE-region window — plus the LOD rings out to `LOD_HORIZON_UNITS` — 15,360 m at the play sizes (256 m regions: factors 8/16/32/64/128/256/512 to 2/3/6/12/24/47/60 regions, ~4,400 LOD keys; 1 km and 80 keys before 2026-11-05 — client/server cost of the 15 km default unmeasured), 1 km at 64/128 (16 regions at the test size, ~1,060 LOD keys). The ring table is not widened for the bigger window: the near window is subtracted from it, so the factor-2 ring (bound 2) is entirely simulated terrain and factor 4 starts right outside it). The variable exports `VOXEL_WORLD`; `VOXEL_NEAR_RADIUS=0..3` and `VOXEL_LOD_RINGS=off|small|full|"2:2,4:4"` override its halves. **View distance**: `just view=<metres>` (`VOXEL_VIEW_DISTANCE_M`, ≤ 16 km; browser `?view=`) builds the ring table by the pixel-budget rule (`game::lod::ring_table_for`: each ring the coarsest factor within `LOD_MAX_CELL_PX` where it starts — it reproduces the shipped tables); an explicit `VOXEL_LOD_RINGS` wins. The haze (`atmosphere::ViewDistance`: exponential, Koschmieder 2 % contrast at the visibility = `VISIBILITY_SHARE_OF_REACH` 0.8 × the rings' reach, so the ring edge keeps < 1 % — an overcast day's ~12 km by default; never sized below a 1 km reach) and the perspective cameras' far plane (`sync_far_plane`) follow it; `VOXEL_FOG_VISIBILITY_M` sets the haze alone; ground picks keep their own 1 km reach (`selection::PICK_REACH_M`); the client logs `[client] view distance: …` at startup. `LOD_FACTORS` doubles 2…512 (128 and 512 added for the 15 km horizon). **Fortress neighbourhood**: on top of the near window, once the server says which fortress the client plays (`ServerPacket::Fortress(Option<HeldFortress { site, region }>)`), the client also subscribes — so the server runs and the client predicts — every region within `WorldScale::fortress_radius` of the fortress region (`FORTRESS_NEAR_RADIUS` = 1: the 3×3 around it in `full`, 0 in `small`/`tiny`; `VOXEL_FORTRESS_RADIUS=0..3` overrides), in BOTH play modes: in Fortress mode the viewer stands there, in Adventure the fortress and its neighbours keep running while the adventurer walks off, and the Adventure camera may pan over the whole neighbourhood while the body is inside it (`commander/bounds.rs` `adventure_window`). `instance.rs` `desired_window` is the one set both the subscriptions and the LOD exclusion use; headless harnesses keep radius 0 (`set_fortress_radius`). At the play recipes' 256 m regions that is 9 simulated regions instead of 1 — its client/server cost is unmeasured. The 32³-voxel render brick (`BRICK_VOXELS`) is baked into packed records, shaders and the LOD math — shrink the window, not that (the sim chunk is its own build dial, below). `just render-bench` honours it too (its readiness gates and JSON metadata follow the active scale; `RENDER_BENCH_LOAD_TIMEOUT_SECS` stretches the 120 s load budget for slow adapters). Use a small world for iteration on weak GPUs, but compare benchmark numbers only within one scale.

**Region size** is a BUILD-time dial, in BLOCKS (1 block = 1 m), so it keeps its meaning when the sim chunk size changes (the old chunk-denominated `VOXEL_REGION_CHUNKS` / `VOXEL_CELL_CHUNKS` now fail the build). The recipes that PLAY the game (`server`, `client`, `run`, `play`, the `-release` variants, `web*`, `diag`, `perf-capture`, `fly-probe`, `shuttle-probe`, `play-test`, the profilers `trace-chrome` / `trace-join` / `perf` / `perf-client` / `perf-server` / `profile-*` / `tracy-client`, and `cross-section`; `scripts/run.sh` too) default to 256 blocks (256 m regions, one-region near window; 512 was the default 2026-10-30..11-02), while tests, `check`, `clippy`, `render-bench` and raw `cargo` stay at 64 (64 m); an explicit `region_blocks=N` wins for every recipe. For experiments: `just region_blocks=128 run` compiles everything with `game::REGION_BLOCKS = 128` (2048-unit / 128 m regions instead of 1024 / 64 m; `crates/game/src/protocol.rs` parses `VOXEL_REGION_BLOCKS` with `option_env!`; `REGION_CHUNKS` / `REGION_BRICKS` / `REGION_SIZE` are derived from it). `REGION_BLOCKS_CHOICES` is 64, 128, 256 and 512 — each has its own `LOD_RING_TABLE` (re-cut to the same pixel budget and horizon) and checked fixtures; the tiling contract in `lod.rs` const-asserts a power of two and anything not in the list fails the build. 256 (4096 units / 256 m, the play default since 2026-11-02) and 512 (8192 units / 512 m) are played as a one-region window (at 512 with factor-16…512 rings out to the 15 km horizon). Old numbers for scale: a 256 m region was a 578 MiB raw snapshot and ~7 GB of server state for a 3×3 window at the old 2-block chunks (~50k chunks per region) — at 16-block chunks a 512 m region is 32×32 chunk columns; re-measure before quoting. The default lives in `.cargo/config.toml` `[env]` so raw `cargo`, rust-analyzer and `just` share one build fingerprint; switching recompiles `game` and its dependents (not Bevy or the forks). Server and client must be built with the same value — there is no connect handshake to refuse a mismatch. Every per-region cost scales with AREA (measured: region start 0.37 → 1.3 → 3.9 s and snapshot 40 → 161 → 578 MiB at 64 → 128 → 256 blocks), so compare numbers only within one region size; findings and the distance-based-window recommendation are in `docs/superpowers/specs/2026-09-20-region-size-investigation.md`. (Cell mode — island-sized regions loaded in cells, which allowed sizes up to 65536 — was removed 2026-10-30: every client simulated every active cell of its region, which cannot scale; regions are whole and players cross seams. `VOXEL_CELL_BLOCKS` now fails the build. Plan: `docs/superpowers/plans/2026-10-30-remove-cell-mode.md`.) Never write the region edge as a literal — derive from `REGION_BLOCKS` / `REGION_SIZE`; `REGION_CHUNKS` counts sim-chunk columns (4 at 64 m, 32 at 512 m) and `REGION_BRICKS` 32-voxel LOD/render bricks.

**Chunk size** is a BUILD-time dial too: `VOXEL_CHUNK_BLOCKS` (`game::CHUNK_BLOCKS`, parsed in `crates/game/src/block.rs`; `just chunk_blocks=N`, default 16 in `.cargo/config.toml` `[env]` and the justfile; legal: exactly 2 or 16 — the only sizes with pinned goldens — anything else fails the build). The **sim chunk** is `CHUNK_BLOCKS`³ blocks — 16³ = 16 m = 256 units (`CHUNK_UNITS`) by default — and is the unit that owns ONE entity, one rapier body and one collider set (block-scale + chisel-scale `Voxels`, or one cuboid when full); the 32³-voxel **brick** (`BRICK_VOXELS`, 2³ blocks) is the render/LOD unit: the server builds LOD from `Chunk::bricks()` views, and the client fans each sim chunk out to `BRICKS_PER_CHUNK_EDGE`³ (8³) brick entities (`renderer/bricks.rs`). Dense voxel arrays exist per brick only (`BrickView::voxels`, the test oracle `derive_voxels(chunk, brick)`), never per chunk. Every literal 32 must say which it is: `BRICK_VOXELS` or `CHUNK_UNITS`. 2 (the pre-2026-10-29 size, where chunk = brick) still builds and passes: hash goldens (`wasm_determinism`, `scene_hash_golden`) are pinned per chunk size, and the seam/slime `physics_goldens` are recorded at 16 and skipped at other sizes. Server and client must share the value; switching recompiles `game` and dependents and keys the worldgen cache separately. Spec: `docs/superpowers/plans/2026-10-29-chunk-size-increase-handoff.md`.

**Builds and tests are capped at 80% of cores** so they never take the whole desktop. A job count alone does not do it — each rustc runs multi-threaded codegen, and 16 jobs still saturated all 20 cores — so the justfile's `cap` variable prefixes every build/test/check/clippy invocation with `nice -n 10 taskset -c 0-<jobs-1>`, pinning the whole process tree (test binaries and their thread pools included) to the first `jobs` cores. `cargo run` and directly-launched binaries are never pinned, so the game and its perf numbers are unaffected. Tune with `just cpu_percent=50 build` or `just jobs=4 smoke`. **Raw `cargo` outside `just` is not pinned** (`.cargo/config.toml` only sets `jobs = -4`, and `cargo test` threads are uncapped) — go through `just`, or prefix `nice -n 10 taskset -c 0-15` yourself. Server-side, `LOD_BUILD_THREADS` sizes the LOD worker pool (default: a quarter of the logical cores, clamped 2..=6 — `crates/server/src/lod_workers.rs`; the server logs the resolved count at startup and `perf-capture` summaries show it).

The game crate has the rollback test suite: `cargo test -p game` (transaction/undo invariants in `tests/log_model.rs` and `tests/simple.rs`, seeded randomized rollback in `tests/random_ops.rs`, vendored-container inverse-op guarantees in `tests/hash_restore.rs`). Rollback correctness bar: `hash(before) == hash(after undo)`, bit-exact. The client has its own headless test suite: `cargo test -p client` (sim-bridge, coordinate conversion, interpolation, async chunk meshing, and full client/server convergence harnesses, run via `MinimalPlugins`/`AssetPlugin` with no window or GPU).

**Do not run the whole game / server / client suites as a routine check — they take far too long** (even the "quick" `just test` builds every game test module and a Bevy-sized client test binary). Verify a change with:

- `just test-one <crate> "<cargo test args>"` for exactly the tests the change touches, always naming the target so nothing else gets built (each crate's integration tests are one `it` binary, `tests/it.rs`, filtered by file name + `::`; the few files that need their own process — they flip the global `HASH_MODE`, pin the forged world, install a logger, run on wasm32 or are release perf gates — keep their own `--test <file>` target, listed at the top of `tests/it.rs`; a new test file that touches process-global state must get its own `[[test]]` too) — e.g. `just test-one game "--test it lod_streaming::pristine"`, `just test-one client "--lib world_scale::"`.
- `just test-threads` (~12 s warm) after touching boundary handoff, the `WorldManager` or `region_threads` — the region is the threading unit (one OS thread per running region; nothing inside a region is parallel), and these are the only tests where a player walks between regions on different threads. Two layers, both tagged slow so nothing else runs them: `crates/game/tests/handoff_schedule.rs` walks across a seam and through a region corner, there and back, under **seeded scheduling jitter** (`game::InlineSchedule` on the `InlineSpawner`: permuted tick order, inputs a tick late, missed ticks — a failure names a seed that replays exactly), and `crates/server/tests/threaded_world.rs` does the same walks on real OS threads, including waking a cold region on the production `with_generator` spawn path. Put scheduling-sensitive correctness in the seeded layer; keep real threads for plumbing. The client twin (`crossing_converges_under_late_region_scheduling` in `crates/client/tests/crossing.rs`) is a slow client opt-in.
- `just determinism-wasm` after touching sim math, the physics forks or anything hashed/serialized: the same scenes must end in identical state on native and wasm32 (node): `crates/game/tests/wasm_determinism.rs` pins a region scene (crc32 of its bincode bytes AND `game::state_hash`, asserted equal on both targets) and an underground dig (crc32 + state hash), and `crates/physics-next/tests/state_hash_wasm.rs` pins the forks' `StateHash` walk. The recipe installs the Cargo.lock-matched `wasm-bindgen-test-runner` under `target/tools` on first use. Behaviour across a physics-engine change is pinned separately by `just test-one game "--test it physics_goldens::"` (tolerance goldens; re-record only on purpose).
- `just smoke` as the general sanity check — **this is the default verification, and it is hard-limited to 60 s** (`smoke_timeout`; ~12 s warm): two game test binaries, the server lib tests, a *type-check* of the server's integration tests (all tagged slow, so nothing else notices them rotting), and a *type-check* of the client (lib + bin + tests). It never builds a client test binary, because that means a full Bevy codegen + link (many minutes cold). Running client unit tests is an explicit, slow opt-in (`just test-one client "--lib <filter>"`) — ask before doing it.

`just test` (whole quick suites) and `just test-full` (`--include-ignored`, minus the release-mode perf gates) still exist for a deliberate broad sweep; run them only when the user asks or a change is wide enough to need them, and say so first. Tests measured slower than 100ms are tagged `#[ignore = "slow: >100ms — run via just test-full"]`, which keeps them out of `smoke`, `test-one` and `just test`; tag any new test that takes >100ms the same way.

Bevy is pinned to `0.19.1` in the root `Cargo.toml`; Bevy's API surface moves fast between minor versions, so treat upgrades as a deliberate, tested migration rather than a routine bump — API drift (renamed types/traits, moved modules, changed system-set names) is a known hazard. The 0.18 → 0.19 migration (2026-09-22) is the worked example: the render graph is gone — custom passes are systems in the per-camera `Core3d` schedule ordered against Bevy's pass systems (`voxel_pull::gpu::add_near_gpu_systems`, `far_voxel::pass::far_voxel_pass`); `MeshPipelineViewLayouts` is built in `RenderStartup`, so pipelines that clone it are created there too; the view bind-group layout is keyed on many view features (fog, tonemapping, …), so custom mesh-view pipelines take their key from Bevy's `ViewKeyCache`, and the WGSL gates fog behind `DISTANCE_FOG`. The shader-validation tests compose against hand-written import STUBS, so an upstream WGSL signature change (0.19 added `frag_coord_xy` to `fetch_directional_shadow`) only shows at pipeline creation — after a Bevy bump, run `just pull-smoke` (self-screenshot of the production pull path) on a real adapter. `renderer::render_plugin()` disables wgpu's `EXPERIMENTAL_COOPERATIVE_MATRIX`, which NVK advertises but then fails `vkCreateDevice` with.

### WASM build (browser multiplayer)

The client also targets `wasm32-unknown-unknown`; in the browser the native
QUIC netcode is replaced by WebTransport (`crates/client/src/netcode_web.rs`):

```sh
cargo run --bin server   # quinn :6466 + WebTransport ingress :6467; writes
                         # assets/webtransport-cert-hash.json for the page
# From the repo root (so ./assets is served). The custom index adds a
# fullscreen canvas + download progress bar:
WASM_SERVER_RUNNER_CUSTOM_INDEX_HTML=crates/client/index.html \

```

`just web` does both: it starts the dev server (built with the same dials; log `target/web-server.log`; skipped if something already listens on UDP 6466) and stops it with SIGTERM — world saved — when the page server exits. Open `http://127.0.0.1:1334/`. **The browser cannot create or load worlds — it only joins a server**: it opens on
the main menu, which on wasm (`frontend::JOIN_ONLY`) has just a server address field and **Join server**
(`ui/main-menu.slint` `join-only`). The field is prefilled with `VOXEL_WEB_SERVER` baked in at build time (`just
web-release` / `deploy` set it to the justfile's `web_server`, the deployed hostname — NOT the `deploy_host` IP:
the WebTransport certificate is Let's Encrypt's for the name), else the page's own https host, else `127.0.0.1`
(`web_endpoint::default_server_address`). Join (`session::PendingServer` → `Starting`, `session::web_flow`) builds
a fresh game manager + WebTransport connection per session (`sim_driver::start_session`; a real hostname /
`host:port` dials `https://host:port/` with its real certificate, a local address pins the dev server's hash from
`assets/webtransport-cert-hash.json`, `web_endpoint::web_server_for`); the first `SetPlayer` enters the world
un-embarked, so the arrival map and embark step show as on native; the connect retries for two minutes
(`CONNECT_DEADLINE_MS` in `netcode_web.rs`), and a give-up or a lost connection ends the session with the reason
(failed start: on the starting screen; lost: on the menu); the Esc menu's Main menu drops the driver, which closes
the transport. Append `?world=tiny|small|full` to pick the world scale (the browser has no `VOXEL_WORLD`; default
full — the debug wasm build is too slow for the full world). `LocalServer` (`crates/client/src/local_server.rs`)
is only the native harnesses' in-process server now. Requires
`rustup target add wasm32-unknown-unknown` and `cargo install
wasm-server-runner`. See
`docs/superpowers/specs/2026-07-05-webtransport-netcode-design.md`.

**Web Workers (browser multithreading)**, `crates/client/src/web_worker/`: Bevy's task pools are single-threaded on
wasm32 and shared-memory wasm threads are out (wgpu drops `Send`/`Sync` on wasm whenever the `atomics` target
feature is on, which Bevy's renderer cannot build without), so the browser build runs **separate wasm instances in
module Web Workers that talk by bincode `postMessage`** (transferred `ArrayBuffer`s) — the same message-passing seam
the native threads keep. `index.html` compiles the module once and publishes it as `globalThis.__orionWasm`
(`{js, module, base}`); each worker is a Blob-URL bootstrap that instantiates that module (wasm-bindgen's start runs
`main`, which returns at once in a worker — `web_worker::in_worker`) and calls the exported `orion_worker_main(role,
base)` (`main.rs`). Two roles: the **sim worker** (`web_worker/sim.rs`, one per session — the native game thread:
`GameInstanceManager` with all packet decoding/encoding, ticking on its own 4 ms timer; the page's
`sim_driver::drive_sim` only forwards the session channels — `ToSim` batches of `GameEventKind` / `ClientRequest` /
the wireframe flag in, `SimOut` batches out, where the per-region `GameDataUpdate` and UI streams, which ride
`ClientUpdateEvent` as channel halves, become messages and the page makes fresh channels for them; the sim worker's
`log` lines are re-emitted on the page; a worker crash ends the session with the reason). **The WebTransport
connection stays on the page** (`netcode_web::connect_frames`: raw frames posted to the worker as they arrive and
decoded there, the worker's encoded frames written in order — byte copies only on the page): a worker-hosted transport
joined fine but once wedged the server's shared writer on that client's stream credit in a debug build under load,
unexplained (see `netcode_web`'s module doc). Found on the way and fixed: the server's writer task blocked a tokio
worker in a crossbeam `recv()`, which froze any WebTransport connection whose task sat in that worker's LIFO slot until
the server next sent something (joins whose first request reached a quiet server died as a "Network blackhole") —
`block_in_place` in `crates/server/src/lib.rs`. The other role is the **compute pool** (`web_worker/pool.rs`,
`navigator.hardwareConcurrency − 2` workers, 1..=6, started on first use and kept for the page's life): every
renderer compute task is a typed `renderer::compute::ComputeJob` (serializable input, pure `run`, serializable
output — near brick meshing `NearMeshJob`, LOD cells `LodMeshJob`, snapshot brick derivation `DeriveBricksJob`
(on wasm it carries only the batch's chunks + face neighbours + ground, `bricks::SnapshotPart`), brick edits
`BrickEditsJob`, voxel bodies `BodyMeshJob`); `compute::spawn(job, then)` returns an ordinary Bevy `Task` —
natively the job runs on `AsyncComputeTaskPool` unserialized, on wasm it is posted to the least-busy worker and a
dead worker's jobs run on the page. A new kind of work goes in `JobKind` + `run_encoded` and must carry everything it
reads (workers have no ECS; they install the embedded block registry themselves). `?workers=0` turns all workers off
(sim and meshing back on the main thread), `?workers=N` sizes the pool. Round-trip tests: `just test-one client
"--lib compute::"`.

### Profiling

Measure in **release** (`just diag`, `just client-release`, the `profiling` profile). The dev
profile is opt-level 1 and runs the hot loops ~2.5x slow, so an FPS number from `just client`
measures the build, not the game. And **always check which GPU you got**: this box exposes four
Vulkan devices (Intel iGPU, an NVIDIA T600 on the NVK driver, the RX 6700 XT, and llvmpipe
*software* rendering), and with no `WGPU_ADAPTER_NAME` wgpu chooses for you — pin it with
`just adapter=6700 …` and confirm against the `AdapterInfo` line in the log.

**Check the power source too.** On 2026-09-19 this laptop was fed by an ~88 W USB-C PD source
(`/sys/class/power_supply/ucsi-source-psy-*`) and the firmware clamped every core to ~400-700 MHz
under multi-threaded load (one busy P-core: 2-3 GHz of 4.6). Bursts run fast, then the clamp
bites, so anything multi-threaded (joins, region genesis, builds) measured several times slower
and noisier than the hardware allows — compare ratios, not seconds, until re-baselined on the
real adapter. Watch `scaling_cur_freq` under load to tell.

## Workspace Layout

First-party crates (workspace members):

- `crates/macros` — Proc macro crate providing `#[rollback]` on the state module. Fields marked `#[undo(cell|map|slotmap)]` get tier-1 wrappers (`UndoCell`/`UndoMap`/`UndoSlotMap`) whose mutating methods log typed, exactly-invertible deltas automatically; `#[emit(insert = ..., remove = ...)]` derives renderer `GameDataUpdate`s from those deltas in both apply and undo directions. Unmarked fields stay `Undo<T>` (tier 2): mutate via `undo_scope()`/`undo()` closures that MUST be true inverses of the full serialized state (`hash(before) == hash(after undo)` is enforced at rollback time), or `change()` for snapshot-restore; `emit_on_undo()` registers compensating render events. Verification has three per-entry modes (`game::set_hash_mode`): `Full` (crc32 of the whole field's `StateHash` walk — the process-global default, used by tests/harnesses), `Delta` (digest of only the entry's mutation footprint), `Off`. The client and server binaries call `game::set_hash_mode_from_env()` at startup: `Off` (`game::DEFAULT_HASH_MODE`, since 2026-11-02 — the per-entry check runs on every undo entry, every edit and every rollback, and Full made "Complete all orders" a multi-second rollback loop) unless the `HASH_MODE` env var (`off`|`delta`|`full`) overrides it; it is independent of the desync check below, which hashes the whole state itself. Desync between client and server is caught separately by the **server's state-hash interval**, every 100 ticks (5 s) in the server binary (`game::DEFAULT_STATE_HASH_INTERVAL`; the SERVER's `VOXEL_STATE_HASH_INTERVAL=N` overrides it, `0` = off; `game::set_state_hash_interval`, process-global, 0 in tests and in-process harnesses): a region hashes its whole state (`game::state_hash`) after each tick with `tick % N == 0` and ships it with that tick's event as `ServerPacket::HashedGameEvent(event, tick, hash)`; the client registers it on the region (`Region::expect_state_hash`) and checks when reconcile confirms that event — free after a misprediction, else its predictions are rolled back for the hash and replayed — logging `[state-hash …] DESYNC` + a `state_hash_mismatch` perf event, a `[client-state-hash] checked= mismatched=` line per metrics window, and the server's cost as `state_hash n= sum= max=` on the `[region …]` line; a single-player server spawned by the client inherits the env (e.g. `VOXEL_STATE_HASH_INTERVAL=0 just run` to turn it off); test `just test-one game "--test state_hash_check"` — `HASH_MODE=full` (whole-field hash per entry; ~4.4 ms per block edit at 16-block chunks and growing with region size) or `HASH_MODE=delta` (per-entry footprint digests) turn the per-entry check back on for debugging an undo closure. Hashing is the `StateHash` trait (`crates/state-hash` + `state-hash-derive`, derived on every state type and in the physics forks), never std `Hash` or serialized bytes. `forged.rs` reads it (`WorldArtifact` v7 (`ARTIFACT_VERSION`): quantised `u16` `QRaster`s for height/uplifted/bedding/`temperature_c`/`precip_mm`, `u8` 0–100 rasters for drainage/volcanism/salinity/biome/savagery, a `u16` region-id raster + region records, volcano sites, edges, lake bodies as cell runs, geology column, river reaches, spawn; zstd over row-delta rasters, ~1.9 B/cell; coast distance is recomputed on load and the height is held only as its `QRaster` (no decoded copy); the body is stream-decoded, so a loaded 16 km / 16 m world costs ~27 B/cell resident (~28 at peak) — ~1 GiB at the generator's 100 km / 16 m, right at the server's 1 GB budget (spec `docs/superpowers/specs/2026-11-01-df-scale-world-terrain-design.md` §6); an older file is refused with `OldVersion` "re-forge this world", shown as "needs re-forge" in the main menu list; read/write is native-only) and serves it through the SAME `generate_region`/`coarse_tile` entry points when a world is installed. **The server serves a forged world by default**: `server::world_file` resolves `VOXEL_WORLD_FILE` — unset/empty = `worlds/default.world` (git-ignored; forged with `ForgeParams::default()` — the 16 km / 32 m continent — on first start if missing, a few seconds; the save is atomic (temp file + rename), an existing file is never overwritten, a corrupt one panics telling you to delete it), `procedural` = the noise world, anything else = that file (`just world_file=<path> run`) — and calls `forged::install` before worldgen first asks. Tests, tools and wasm never run the server, so they stay procedural unless `VOXEL_WORLD_FILE` is set (`forged::active()` keeps the env fallback: `procedural` = no world there too, relative paths from the repo root like the server). With a world the `seed` argument is ignored, the disk cache is keyed by the file's crc, a set-but-unreadable file panics rather than mixing worlds. Generated terrain is **whole blocks and half blocks only**: the surface is rounded to the nearest half block (`HALF_TEST_M`/`FULL_TEST_M` in `lib.rs`), and a half block is NOT a special block type — it is ordinary `ChiselData` holding one cuboid (`ChiselData::cuboid`), so it is voxel-editable like any chisel. A submerged surface block is always whole (a half block's empty upper half would be an air pocket). `examples/quantize_probe.rs` reports region cost + step walkability. Both paths build blocks from a `Patch` (column profile + topmost water block per column): forged patches interpolate the raster bicubically on the usual 4 m lattice, then carve river channels, levees and lake berms per point so water above sea level is contained (water surfaces snap to whole blocks). Forged column profiles are **unbounded** (`ColumnProfile::unbounded`: no density ramp, surfaces scanned in `FORGED_SCAN_TOP`/`BOTTOM` = 4096/−1024 blocks; procedural keeps the 320/−64 ramp band, bit-identical), the surface scan starts at the analytic `surface_y()`, and a forged coarse LOD cell column fills down to its lowest face neighbour's surface so steep faces have no gaps (procedural coarse tiles keep the soil-band fill). **Biomes at walking scale** (forged worlds only; with `Materials::biome` = `BiomeBlocks::NONE` — hand-built test materials — forged columns keep `material_at`, and the procedural world never changes): each block column takes the biome of the cell nearest its point displaced by up to `BIOME_DITHER_M` (24 m, a 2-octave noise — `ForgedWorld::biome_at`), so borders are irregular; `Materials::ground_cover(biome, above_snow_line, y)` gives surface / soil / soil depth per biome (temperate = `material_at`'s grass/dirt with beaches; savanna dry grass, taiga podzol, tundra frozen dirt over gravel with snow patches, desert 8 blocks of sand, wasteland gravel, badlands red sand, marsh/swamp mud over peat, mountains thin soil (beach sand at the shore), glacier bare rock; every submerged column (sea, lake or river floor) keeps `material_at`'s sea-floor sand whatever biome the dither gives it, and snow lies on dry ground only; `AIR` = the recipe's rock), snow on top above `ForgedWorld::snow_line_m` (where the temperature reaches `SNOW_LINE_C` = −2 °C), salt flats around closed salt lakes; lake and sea water under 0 °C freezes `ice_blocks` (1–4) whole blocks from its top (rivers stay liquid, past a sea edge too, so LOD shows no seam), and dry glacier columns carry `glacier_ice` (1 block per °C below 0, 4–40, thinned by the bilinear share of glacier cells towards the edge) whose top IS the `ColumnGround` surface (implied ground, bedrock depth, pathing and the x-ray all see the ice top; bedrock stays `UNDERGROUND_DEPTH` under it, so ≥ 20 blocks of rock under 40 of ice). Region generation and `coarse_tile` share one per-column sample (`lib.rs` `point_sample` → `ColSample`), so LOD shows the same surface blocks; trees never stand on glacier, salt flats, desert/wasteland/badlands/tundra cover, marsh mud flats or non-forest snow (swamps and mangrove swamps are forested wetland and keep theirs). `just cross-section --world …` prints the region's dithered biome shares. `just world-map --world <file>` renders a forged world exactly as the generator samples it (`--layer biome|temperature|precipitation|drainage|regions` adds the world's own rasters in the world map's colours, ramps in `tile_map`: `temperature_color` / `precipitation_color` / `drainage_color`; the forge previews (`forge::render::PreviewLayer`, the forge-ui buttons) share them); **seed search** (`just forge-proto --search N`) scores by `forge::quality::world_score` (DF-style: land share 30–60%, ≥3 peaks above the snow line (`forged::SNOW_LINE_C`), ≥3 mountain regions bordering other land, ≥3 forest regions, a Strahler ≥4 river, ≥10 biomes, a glacier when a pole is on, regions ≤ `REGION_CAP` 2750; terms multiply as 0.15 + 0.85·term) and the forge report adds rivers by order, temperature/precipitation ranges and snow-line peaks; every height map (the minimap, the world map, the forge previews) colours land by the one ramp `tile_map::height_color` (to 3,500 m, snow above `SNOW_LINE_M`), and the tools' 16-bit heightmaps span −1,000…+3,600 m. `just cross-section [--world <file>] [--region X,Z] [--axis x|z] [--at <block>]` writes a vertical slice PNG of the generated ground (soil, rock layers, bedrock) and prints the centre column's strata. **Trees** (`trees/`): `skeleton(species, seed, age)` is a parametric recursive skeleton (trunk → limbs → branches, per-species `ShapeParams` in `SPECIES`, angles from the integer `SIN_TABLE`, fitted inside the species' crown radius and height; a younger skeleton is a prefix of an older one) and `rasterize` turns it into `TreeBlock`s (whole or voxel-masked `Log`/`Branch`, whole `Leaves`); look at one with `just tree-view --species <name> --seed N --age N [--grid]` (front/side/top PNGs, or a 3×3 seed sheet, in `target/tree-view/`). `trees_in` places them order-independently on a `TREE_LATTICE_BLOCKS` lattice where the species' climate niche allows (no water, no crown across a region seam). Species (`SPECIES`, append only): oak, pine, birch grow anywhere their niches allow (the procedural world's only trees, bit-identical); spruce (taiga cone), acacia (savanna umbrella), palm (tropical coast — salinity niche, 0 inland), jungle (tall, buttressed `base_flare_pct`, broad canopy) and cactus (saguaro, `leafless`, one `cactus` block) grow only in a forged world, in the biomes their `Species::biomes` list (`Habitat::biome` = the column's dithered biome; procedural `None`); `NATIVE_ONLY_BIOMES` (deserts, jungle, mangrove) grow only species that list them, `BIOME_TREE_DENSITY` scales the chance per biome (forests 1, jungle 1.4, savanna 0.15, grassland 0.05, deserts 0.02), and a forged cell whose chances sum past 1 picks the species in proportion; forged moisture saturates at `FORGED_MOISTURE_SATURATION`. Generated terrain writes them as `<sp>_log` / `<sp>_branch` / `<sp>_leaves` blocks (a `single_block` species is its one block, which `game::SINGLE_BLOCK_TREES` makes trunk wood for chopping) carrying the tree in `Block.data` (`Block::with_tree(id, tree, limb)`: bits 0..18 the tree id — `tree_id()`, 0 = not a tree; placement's id is `lx mod 512 | (lz mod 512) << 9`, unique within any 256-cell neighbourhood — and bits 18..24 the limb — `limb()`: 0 for the trunk, else `(ordinal % 63) + 1` of the level-1 skeleton node it grows from (`TreeSkeleton::limbs`, stable as the tree grows); wood takes the lowest limb of the segments filling it, leaves their cluster's). Per-block props come from the manifest (`game::block_props()`: `is_solid` — leaves are not, so they have no collider; `is_cutout` — leaves draw alpha-cutout; `collider_scale` — wood collides on the half-block grid). Block textures: `just tree-textures` (oak/pine/birch, `tools/textures/tree_textures.py`) and `just block-textures [--sheet]` (the biome / ice / tree-species textures, `blocks.ron` ids 22+, mostly recoloured from existing PNGs — `tools/textures/gen.py`); both deterministic Pillow scripts writing `assets/blocks/`, new PNGs also go in `EMBEDDED_BLOCK_TEXTURES`. Growth is not built. **Tuning the forge:** every tunable lives in one runtime table, `crates/worldgen/src/forge/knobs.rs` (its defaults ARE the tuning — they build ~2 km ranges on the 16 km continent and 2–2.5 km on the island, `max_peak_m` caps relief at 2,800 m (≤ 3,500), the geology column reaches `COLUMN_BOTTOM_S` = −5 km; CLI `--set <knob>=<value>`), and `just forge-ui` serves a local page (`serve.rs` + `ui.html`, std-only HTTP on 127.0.0.1:8787) with each knob as a slider and a live map preview — a change re-forges at 64 m cells in ~1.5 s; layers rivers/relief/geology/rain/before-erosion, press-and-hold for the previous render, "Copy as flags", "Save world file" (forges at 16 m). Coarse previews under-count lakes and peaks — check at 16 m before keeping a value. Unset, nothing changes — procedural tests never see it. Depends on `game` (not vice versa) — generation is injected into the `WorldManager` as a closure. `coarse_tile` point-samples one profile per LOD cell column for every block-scale-or-coarser factor (16/32 per region, 64/256 per tile; ~40× cheaper than generating the region, and exact at factor 16) — the cheap pristine-terrain base the server overlays authoritative regions onto. Water fills through `SEA_TOP_BLOCK`, so the sea surface is `SEA_LEVEL` = 1024 voxels, a multiple of every LOD cell: any-solid downsampling rounds surfaces up a cell, and a sea off that lattice shows as a wall at ring boundaries.

## Vendored Forks

`crates/rapier`, `crates/parry`, `crates/slotmapd` and `crates/block-mesh` are vendored, locally patched forks wired in via `[workspace.dependencies]` path overrides. Everything else (glam/`glamx`, `nalgebra` 0.35 and `simba` 0.10 inside rapier, `approx`, `ordered-float`) comes from crates.io — the old nalgebra/simba/approx/ordered-float forks were dropped in the rapier 0.36 switch (upgrade plan `docs/superpowers/plans/2026-09-22-rapier-035-upgrade.md`, decision D4), and glam is deliberately not forked.

- **rapier 0.36.0 / parry 0.31.1** (import commit `bb7d5b5`, pristine upstream). Every hunk that differs from upstream carries a `// mmo-fork:` marker (`grep -rn "mmo-fork" crates/rapier crates/parry`) and is pinned by a test in `crates/physics-next` (the forks' test crate; `just physics-next-upstream` runs upstream's own determinism/regression tests against the forks). Updating to a newer upstream is a re-import plus re-applying the marked hunks, not a version bump. The patches:
  - **Rollback.** The hybrid `StepJournal` (`pipeline/step_journal.rs`, `PhysicsPipeline::step_journaled`): first-touch capture of bodies/colliders in the set accessors plus per-tick clones of the island manager, narrow and broad phase, reverted exactly (`StepJournal::revert`; digests `pre_digest`/`revert_digest` for `HashMode::Delta`); the arena/set inverses the game's undo closures call (`alloc_state`/`revert_insert`/`restore_raw`/`pop_modified`); pipeline memo invalidation after a revert (`IslandManager::journal_reverts` epoch).
  - **`StateHash`** derives and hand impls on ~160 rapier/parry types (cached digests: the voxels content hash, sorted broad-phase pairs, island joint links); serde-skipped workspaces are `#[state_hash(skip)]`.
  - **Mass properties.** Fixed bodies skip the collider mass properties (their voxel shapes would otherwise go through std `acos`/`cos` in glamx `SymmetricEigen3`, a cross-target hazard), and a body-type change triggers the recompute.
  - **Shape casts and the character controller** (walking on voxel terrain): the voxels shape cast's search domain, internal-edge normals and resting contact without ray casts; grazing starts in the support-map cast; `QueryPipeline::cast_shape_on_continuous_surfaces` (flush seams are not edges), whose TOI ties are ranked blocking → least-opposing → lowest collider index instead of BVH traversal order; the KCC snap gate and flush-seam handling; the KCC `depenetrate: bool` gate (plan D7 — the game sets it `false` and keeps `movement::depenetration_lift`). Pinned also by `crates/game/tests/shape_cast_grazing.rs`, `walking_smoothness.rs`, `sunk_body.rs` and `physics_goldens.rs`.
  - **Kinematic sleep.** Upstream 0.36 put kinematic bodies to sleep at zero velocity despite `can_sleep(false)`; `RigidBodyActivation::update_energy` honours it (physics-next `kinematic_sleep.rs`).
  - Packaging: self-contained `Cargo.toml`s (upstream inherits from its own workspace).
- **Determinism** comes from upstream features, not patched math: `rapier3d`'s `enhanced-determinism` (simba on `libm`, glamx on `libm` + `scalar-math`); no `parallel`, no `simd8`, and no inherent `f32` transcendental in a sim path (use `libm::`). The rollback hash is our own `StateHash` trait (`crates/state-hash` + `state-hash-derive`): `f32` hashes canonical bits, `usize` as `u64`, so hashes agree on native and wasm32 (`just determinism-wasm` checks it). The game steps physics once per region tick at `dt` = `movement::TICK_DT` with `length_unit` = `movement::PHYSICS_LENGTH_UNIT` (16 = `UNITS_PER_METER`).
- **slotmapd** exposes exact LIFO inverses (`revert_insert`/`revert_remove`) the undo log needs; **block-mesh** (used by `game`, `client`, `worldgen` for meshing helpers) is not physics and was untouched by the switch.

Changes to simulation math anywhere in these forks can break determinism between client and server: run `just determinism-wasm` and the physics-next suite after touching them.

## Conventions

- Serialization over the wire is `bincode`, framed by `game::encode_packet` / `decode_packet` (`crates/game/src/protocol.rs`): one format byte, and packets above `PACKET_COMPRESS_THRESHOLD` are lz4-compressed (`lz4_flex`; a region snapshot goes 40 MiB → 0.9 MiB). Every transport edge — server writer + QUIC/WebTransport ingress, native client, wasm client — must use that pair; never call `bincode` on the wire directly. State hashing uses `crc32fast`.
- Cross-thread communication uses `crossbeam` channels (game loop ↔ network loop ↔ render loop); async (tokio) is confined to the QUIC networking edges.
- Editions are mixed intentionally: older crates are 2021, newer ones (`macros`, `worldgen`) are 2024.
- `TODO.md` tracks the current high-level direction (the Dwarf Fortress direction's next step, plus the multi-region follow-ups).
- The root `justfile` is the canonical set of build/run/test commands — use it, and edit it whenever the underlying commands change so it never drifts from reality.
